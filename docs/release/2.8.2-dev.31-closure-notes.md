# 2.8.2-dev.31 · 分镜时间语义与 UI 收口审计

## 用户报告与直接证据

用户提供了 324 秒视频的两张 12 格官方低清 videoshot 分镜和完整视频感知 Debug JSON。真实采样时刻 40 秒的画面尚在大厅通道、55 秒在柜台附近、65 秒已到楼梯附近、70 秒附近呈现楼梯动作；本地 1B MiniCPM 的描述却提前将楼梯场景放到 40 秒。模型回执在“9. 90.0秒：”被截断，`visual.description`、`modelDescription` 和 Life `observations` 都只有第一张分镜的部分内容，生产却标为 `analyzed`。所选 24 个时间索引、2 张 Debug JPEG 本身并非缺图。

## 根因与修复

- `lib/preview_vision.py` 过去将两张甚至四张 12 格 JPEG 放在**一次** Ollama 消息中，`num_predict=720`，只要求任意非空文本，没有检查 Ollama `done_reason`、文本末尾和分镜覆盖情况。
- v10 使用每张分镜一条本地独立推理，带显式 R1C1..R3C4 时间坐标；逐张记录状态、内容和错误。如果有任意一张未完成，就只在临时 Debug 中显示已完成部分，整个 `visual.status=vision_incomplete`，不传递模型输出为可信完整视觉观察。
- Node `video-perception-handoff` 保留分镜级独立 `observations` 和 `boardInterpretations`，标明 `model-generated-unverified`。Life 感知候选提示选用每张分镜的有界摘要，避免后续仅取首 600～850 字导致第二张隐身。单个采样秒数的真实来源可验证，**语义是否描述了那个画面仍需人工或更强视觉模型核实**。
- `PREVIEW_BOARD_VERSION=10` 防止本次错误的旧 v9 模型描述缓存被当成新结果。真实 FFmpeg 原视频复查、已有限流、时间预算、账号隔离和发送保护不变。

## 保留风险

1. 1B 小模型可能把同张 4×3 图格的视觉内容错配，即使报告格式/时间属于允许集合。时间码校验不能证明视觉内容正确；遇到精确动作时间，应放大原始 JPEG、用更强模型或真实原视频窗口二次核验。
2. 本次未访问用户本机 Ollama、B站账户或实际 Windows DSH。逐张识图的实际耗时与模型效果需要用户在 12 / 24 / 48 档下分别验收。
3. M2 时间邻近不等于音画语义互证，M3 十一类上下文送达的真实端到端验收仍独立存在；完整 Windows Node/Python 测试由维护者在目标机器执行。

本批只做受影响 Node/Python 定向回归、项目静态/架构/测试治理、npm dry run、补丁回放。未执行真实 DSH 发布，也不应在通过实机全量前标记 2.8.2 正式版。
