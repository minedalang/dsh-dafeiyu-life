# 2.8.2-dev.14 · 原视频安全降级与长视频 Whisper 代表性语音抽样

> 状态：离线增量实现，非正式发布；真实 Windows/DSH/B站需要维护者验收。事实依据为 2.8.2-dev.13 的实际代码及用户提供的一次 22 分 44 秒公开视频感知回执。

## 发现与因果

1. `lib/asr.py` 使用 `yt-dlp` 下载完整 `bestaudio` 音轨，并将整个本地音频文件送入 `WhisperModel.transcribe()`。默认 `small`、CPU、`int8`、`vad_filter=True`、`beam_size=1`。这可解释长游戏视频等待较久，但原日志缺乏分别测量下载、模型加载和转写耗时，**不能精确断言各自贡献，更不能仅凭重复倒计时认定转写质量差**。
2. 用户关闭 Whisper 后视频感知 Debug 明显变快，支持“语音处理是主要瓶颈”的推断，不能据此判断视觉模型有故障。
3. 视频自适应取帧在 `progressive` 单个 `durl` URL 被严格 CDN 校验拒绝时曾直接抛出异常，即使官方 `DASH` 还有不同轨道，也未尝试。`unsafe_video_source` 先前过于笼统，无法定位安全校验不兼容的类别。

## 本轮实施

- 长度 **≥480 秒**、已下载到本地、具有可探测音轨时，默认通过本地 FFmpeg 提取原声时间轴上**开头、中间、结尾**三个各 **60 秒**的 WAV 片段，交给原来的 Whisper 模型逐段处理。原视频 1364 秒的示例窗口为 `0–60`、`652–712`、`1304–1364` 秒：转写处理音频总长从约 1364 秒变为 180 秒（不计下载、解码开销；实际时间未作实机承诺）。
- 此优化不绕过官方字幕优先策略，不扩大 ASR 授权。**音轨仍由 yt-dlp 完整下载**，采样优化减少 CPU 推理量而非下载体积或总网络访问。缺少 `ffprobe`/`ffmpeg` 或无法安全提取时使用原完整转写，不伪造时间码；运行进程超时仍受现有门禁约束。
- `BILI_ASR_LONG_VIDEO_MODE=full` 可由维护者在实际承载 DSH 的进程环境设置，强制长音轨完整识别；默认 `sample`。运行模式不是 AI 或外部内容可以修改的参数。
- 每段 ASR 时间戳加回原始时间偏移；回执写 `coverage=representative-windows`、音轨时长、采样时窗，Life 的交接还声明 `sampled-audio-not-full-transcript`。模型不应把片段当成全片完整台词。没有语音片段不代表视频没有声音。
- 首个官方 `durl` 地址安全校验失败时，继续读取**另外一次官方 API 请求**中的 DASH 源，独立使用同一白名单、SegmentBase 字节索引、字节预算、SSRF/重定向/身份和 FFmpeg 安全条件验证。**绝不请求被拒绝的 progressive URL**。
- URL 校验不开放新域名/路径，仅区分 `video_source_scheme_rejected`、`video_source_authority_rejected`、`video_source_domain_rejected`、`video_source_path_rejected`、`video_source_format_rejected` 五个定长原因。任何原因都不能包含具体 CDN Host、带签名的 URL、凭据。失败后仍按原策略安全降级到 B站官方低清 videoshot。
- 管理中心运行诊断对低清 fallback 展示原因，不把 `videoshot` 当真实解码，不把只读试运行当自主观看。

## 尚未解决

- 没有任何日志可证明某一个被拒绝的真实 CDN URL 绝对属于合法新格式。**本轮不扩展白名单**。需要在升级后的诊断中取得脱敏拒绝分类与正常/深入两种回执，才能决定是否存在需增补的安全规范。
- 单次 Debug 仍会在实际视觉前等待字幕/Whisper；本轮减少长视频推理量，但尚未把两个任务独立并发，也未实现 B站音轨分段安全抓取。后两项应先设计网络预算和生命周期隔离后逐批实现。
- 用户之前的 Windows quick/full 中有其他失败和安全符号链接 SKIP，本批定向测试不能视为修复或放行。
