# 2.8.1-dev.3b.33.10 — Windows DSH 视觉 Python 错误分类与隔离修复

## 11 月 17 日实机证据

- 基础 `.venv` 曾在普通权限下无法写入 TEMP 与项目目录（`PermissionError`）。普通 Conda Python 在那两个目录可写，并已通过同一 DSH 默认/安全 overlay 的四项只读配置测试。
- 用户已经在管理中心填写 `G:\Anaconda3\python.exe`，但仍出现 `runtime_permission_error`。33.9 实际选择器把主 `.venv` 排在显式视觉 Python 前面，全部候选失败后使用首个失败原因，因而不能据此认定 Conda Python 也遭遇权限拒绝。
- 导出的 10:10 日志没有每个解释器的模块检查或对 Duty Home 的单独写入结果；不认定 `mcp` 模块肯定缺失，也不认定用户写入设置未保存。

## 本轮修复

- `index.js`：显式视觉解释器先于主 `.venv` 检查；不改 Life、私信、安全 overlay、MCP nonce 与模型最终回答要求。
- `vision-python-runtime.mjs`：固定标准输入、无 shell 的写入探测分别标记 TEMP 和 Duty Home；按固定模块白名单回报缺失依赖，使用显式视觉路径自己的失败理由，不回显命令输出/环境变量、私信正文或配置。
- `tools/repair-dsh-vision-python.ps1`：提供只读 `-ProbeOnly`，与完整退出 DSH 后的显式构建。仅新建 `DutyHome/.vision-venv`；备份旧视觉环境并在失败时尝试恢复。使用 `G:\Anaconda3\python.exe -m venv --copies`，再安装 requirements，复检新解释器是否可在普通权限下写入以及是否具备 `mcp/bilibili_api/qrcode/PIL`。从不修改主 `.venv`，用户必须手动把输出的新路径填写到 AI 模型设置中。
- `repair-dsh-python-runtime.ps1`：如果用户另外显式修复主环境，创建解释器时优先使用健康 Conda Python 的原生 venv，不再先通过 `uv venv` 创建。

## Windows 操作步骤

普通 PowerShell、项目源码根目录：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\tools\repair-dsh-vision-python.ps1 -BasePython 'G:\Anaconda3\python.exe' -ProbeOnly
```

只读测试如果提示缺少 MCP 模块，只能说明 Conda base 不适合**直接**作为视觉执行器；完整退出 DSH 后执行不带 `-ProbeOnly` 的同一命令，新建与主环境分离的视觉 `.vision-venv`。

成功后将管理中心「视觉专用 Python 完整路径」设置为打印的 `...\.vision-venv\Scripts\python.exe`，手工保存，重启 DSH 并运行图片真实验收。新环境健康通过仍不代表 DSH 子会话已取得 MCP 图片回执或模型最终回答。

注意：依赖安装可能需要网络。禁止管理员运行、修改 ACL、删除主 `.venv` 或清空 Life 数据。Windows PowerShell 5.1 尚需本机验证。
