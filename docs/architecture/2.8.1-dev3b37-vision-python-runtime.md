# dev.3b.33.7 — Windows DSH 视觉 Python 运行时权限与定点修复

## 来自 Windows 实机的已知证据

- 管理员模式：UV venv Python 下 DSH 默认、Node 桥接、两种 overlay 配置导出 exit=0。
- 普通用户：相同 UV venv Python 下四项 exit=1，stderr 安全归类 EPERM；同样的解释器在 TEMP/CWD 的普通文件写入失败。
- 普通用户 Conda Python `G:\Anaconda3\python.exe` TEMP/CWD 写入成功，四项 DSH 配置导出 exit=0。
- 用户并未实测 Conda Python 已安装 B站 MCP 及 Pillow。基础配置导出通过 **不等于** 它可以运行视觉 MCP，更不等于模型已经理解图片。

## 改动范围

- `lib/vision-python-runtime.mjs`：独立 Python 标准输入健康探测，限时、无 Shell；仅接受绝对的普通 `python.exe`，测试 TEMP、工作目录实际文件写入和必要 MCP/Pillow 模块，避免通过 `icacls` 大范围授权。
- `index.js`：人工验收包装器、嵌套只读 MCP 使用同一健康 Python，失败明确为 `python_runtime_unhealthy`；生产视频 overlay 将受检 Python 下发到原有 MCP；加载脚本后不会跨帐号修改 B站凭据、私信状态。
- `vision_dsh.py` / vendor MCP：生产视觉通过限长 stdin 请求启动健康 Python 内的 read-only 描述工具，继承既有 DSH 受限 overlay、MCP 图片回执、源视频网络预算与模型答案校验；旧受限解释器不被用作新视觉模型执行器。
- 主依赖安装：显式修复时备份旧 `.venv` 并用健康基础解释器执行 `uv venv --python <受检 Python>`，只有创建后读写与 MCP 包检查通过才写配置。失败尝试恢复旧环境，绝不直接删除。
- `tools/repair-dsh-python-runtime.ps1`：DSH 完全退出后，在普通 PowerShell 下执行的离线修复方式；先验证基础 Conda Python，旧环境改名备份，安装主依赖并对新 `.venv` 进行普通权限读写验证。失败尝试恢复备份。只读密码/凭据的代码不存在。

## 为什么不提供 `uv --grant-permission`

`uv venv --python` 能指定解释器，但创建环境不改变进程完整性级别，亦不能覆盖系统针对程序的访问控制。`icacls` 可以改变文件 ACL，但本机证据未证明是哪个对象拒绝，给 `.dsh` 目录所有人完全控制是不安全且可能无效的。推荐从健康解释器创建新环境，再对 **最终 `.venv\\Scripts\\python.exe`** 做普通权限读写验证。

## 本机验收步骤

1. 重启 DSH，打开 AI 模型 → 视觉识别 → 技术诊断，查看 Python 健康状态。可在高级框设置 `G:\Anaconda3\python.exe`，但只有安装了全部 MCP 依赖才会被接受。
2. 如果找不到健康且具备依赖的 Python，完整退出 DSH，使用普通 PowerShell 在完整源码目录执行 `tools/repair-dsh-python-runtime.ps1 -BasePython 'G:\Anaconda3\python.exe'`。不使用管理员权限；新建环境不能写入则会阻断/恢复旧环境。
3. 完整重启 DSH，先确认配置导出成功，再执行真实固定图片验收；要求 nonce 绑定图片回执、模型最终中文描述和人工确认全部齐全。
4. 切勿删除 Life 私信续办/回执/限流账本，勿为绕过配置检查取消安全 overlay，勿仅依据独立 MCP ready 或 exit=0 宣称模型识图成功。

本地 Linux 增量测试并不证明 Windows 文件/进程策略下的实际修复结果。
