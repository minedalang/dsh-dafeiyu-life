# 2.8.1-dev.3b.26：私信分享卡片与 Windows 黑窗口归因

## 私信分享卡片

B站私信 `msg_type=7` 表示通用分享卡片，卡片 `source` 决定目标类型。`source=11` 是动态，实际链接位于 `url`，不能只取 `bvid` 或把卡片统一标成视频。旧解析器会将卡片转换成 `[分享视频] 标题 / 作者`，并丢弃 `url`，导致后续 Life 只看到文字，没有可供安全解析的动态链接。

本版按 `source` 分类，并仅将 `parseBiliShareUrl` 接受的官方 HTTPS B站链接写入短期消息文本，供原 `onIncoming → friend-shared-bili-link → Life inspect_shared_link` 链路提取。`source=11` 缺少 URL 时，只在 ID 是安全整数或数字字符串时构造官方动态 URL；不从不安全的大整数 JSON 值重建 ID。`source=5` 只从有效 BV 构造视频 URL。`msg_type=13/14` 只保留白名单 URL；外站地址被丢弃。旧 `msg_type=8` 不再冒充分享卡片。

普通私信监听、定向遗漏复核与 `dm-contact-recheck` 使用相同的用户消息类型白名单。私信原文仍留在原有私有会话上下文，不新增日志副本；动态/视频内容是外部不可信资料，不是工具调用指令。是否查看仍由 Life 自主决定，点赞/评论仍需独立授权和原写入门禁。

## Windows 黑窗口

此前 15 分钟采样记录了大量 Python 与 conhost 进程，但没有可见窗口所有者。`conhost.exe` 存在本身不证明窗口可见。11:09:20 附近的进程事件显示 `DeepSeek Harness.exe` 启动后出现 Python 子进程，与手动视频 Agent 时段相邻；这只能把怀疑范围缩小到 DSH 子进程链，不能确认哪个 PID 创建了用户看到的黑窗。

本版采集器在启动时记录现存进程名/PID/父 PID 快照，给已存在的父进程补足名称；新进程事件也记录父进程名称。可见窗口枚举频率提升到约 40ms，记录 `ConsoleWindowClass` / `CASCADIA_HOSTING_WINDOW_CLASS` 及受限工具进程的可见窗口所属进程、PID、父 PID、父进程名、窗口类与可见状态。绝不采集窗口标题、命令行、完整路径、截图、消息正文或凭据。

采集器仍可能漏掉短于轮询间隔的窗口，也不修改 DSH 内部进程启动选项。根因修复必须以 `console-window-events.csv` 中的可见窗口 PID 为依据，再核对 DSH/MCP SDK 的实际版本与 spawn 行为。禁止仅根据 conhost 数量猜测，也禁止未经 stdio 兼容测试就改用 `pythonw.exe`。
