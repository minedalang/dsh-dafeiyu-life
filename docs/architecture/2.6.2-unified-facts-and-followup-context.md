# 2.6.2 · 统一真实经历事实视图与可辨识待办回访（已实现 / RC）

> 开发说明，非 README 功能清单。版本保持 2.6.2 dev，尚待 Windows DSH Desktop + B站真实账号验收。

## 问题与修复边界

此前真实只读待办已显示完成，但不同聊天入口可能只读到推荐候选、旧聊天或可衰减经历，而不知道任务已经执行。同时，多条待办的自主回访可能只说“刚把那几个视频的资料翻了一遍”，让收件人不知道鱼鱼指的是哪一项。这是 **进度事实可见性** 和 **回访主题可辨识性** 两个独立问题；后者不是模型记忆模糊的借口。

本轮不复制一套永久记忆：`lib/verified-life-facts.mjs` 将当前可用的真实操作回执映射为短期、分渠道、分 UID 的 `VerifiedLifeFact` 视图；`lib/todo-followup-context.mjs` 从现有父子待办账本解析原请求主题。两者共同用于发言，不覆盖人格、意愿或平台权限。

## 数据契约

- **真实来源**：只允许已认证操作适配器构造事件；`operation` 和 `type` 一一对应，必须 `ok===true`，需要真实 `sourceId` / 特定外部回执。模型文本、标题和长期主观感受不能自证操作。
- **类型**：`video_selected`、`video_metadata_read`、`video_visual_inspected`、`audio_playback_verified`、`video_uploaded_verified`、`todo_read_completed`、`message_sent_verified`。单纯 `watch_video` 待办执行成功，当前只投影 **公开元数据已读取**，绝不自动写成已看到画面或听到了音频。
- **待办完成**：`owner-todos.json` 是已接受待办的事实账本，只有 `done` + `completedAt` + 历史中的 `收到成功回执` 才投影成只读完成事实。人工点“完成”不冒充执行回执。事实的时间来自 `completedAt`，不是用户打开聊天时重新盖一个当前时间。
- **作用域**：`public`、`owner-private`、`recipient-private`。非公开必须匹配原真实 UID；还要匹配目标渠道，默认仅使用最近 24 小时的事实视图。没有任何路径从人生记忆 archive 或旧搜索缓存“补记”失去的感官细节。
- **对外文本**：`verifyLifeOutbound` 在模型生成之后、真正平台发送之前核验明确的第一人称投稿、音画经历及 BV 链接来源。能说事实，也能说推测和感受，但不能把“查阅资料”升级为“亲耳听完”或“自己投稿”。明确否定语句（例如“我还没听过”）不会被误判为肯定经历。
- **链接**：本轮已核验读取结果、当前可见成功只读任务的对应 BV，或**当前对方消息明确给出的相同 BV**，才可以构成外发链接来源；过往搜索缓存不是本轮证据。

## 接入矩阵

| 自动生成入口 | 使用共享核验 | 外发前位置 | 额外来源 |
|---|---|---|---|
| 普通 B站私信 | 是 | `dm-autoreply.mjs`，发送占位前 | 当前已完成待办的收件人私有事实、当前来信 |
| 主人 B站私信 Agent | 是 | `owner-dm-agent.mjs`，发送占位前 | 本轮成功只读工具执行记录 |
| 评论 / @ / 动态评论 | 是 | `comment-interact.mjs`，发送占位前 | 评论上下文真实读取、同一 UID 评论待办 |
| 主人评论 Agent | 是 | `index.js` 评论发送适配器 | 同一 UID 的当前事实 |
| 自主私信分享 | 是 | `social-intentions.mjs` 草稿发送前 + `index.js` 平台适配器 | 真实可见的短期事实 |
| 自主待办回访（评论或私信） | 是 | `owner-todo-followup.mjs` + `index.js` 平台适配器 | 同一 UID 原始待办与执行回执 |
| 生活动态 | 是 | `daily-dynamic.mjs` 发布占位前 | 原有可衰减公开经历选择器与文本质量闸 |

明确区别：**用户主动命令的手动发布工具**另有确认、权限和回执机制，不能把“模型自动聊天核验”误当成主人手动操作的授权或阻断。主 Session 是宿主通道，插件不劫持宿主模型所有输出；主 Session 记忆同步仍按原有权限设计。

## 父子待办回访的任务锚点

1. 定位本条 `pending` 的原始 `taskId` / `groupRoot` / 原消息 ID / 来源 UID，原父待办优先；验证父子任务和收件人一致，拒绝跨人读取。
2. 优先使用 **原父待办 title / topic**；仅在可判定时退回同源任务主题 / 可信 BV；`已汇总 3 项相关视频资料` 这种汇总数字不是一个可辨识的原始请求。
3. 将原请求主题、是否合并子待办送给意愿模型，使其自然地提到“这次在回应什么”。鱼鱼仍可 `reply/defer/skip`，此操作不让系统强制联系。
4. 真正发送前，如果文案仍只说“那几个视频、刚查了些资料”，在原文前加一句很短的真实主题背景；若已经明确说明主题，不重复套模板。
5. 如果原请求身份不匹配、缺少任何可信主题、正文引用别的任务 BV，停止发送并在回访诊断中记录原因。**不会猜测那个用户到底说过什么。**
6. 出现平台发送回执不确定时保持 `uncertain`，绝不因为重试“补背景”重新发送；已有去重、安静时段、配额和渠道授权保持原样。

## 预期回复范例

- 不合格：`刚才翻了一下那几个公开视频的资料，具体内容我还记不清。`
- 可辨识、诚实：`说起你之前提的「听大肥鱼翻唱的歌」——我查了几条相关公开视频的公开资料，已经留下查询记录。不过我还没有能证明自己完整听过音频的经历，所以不想假装评价唱得怎样。`
- 无需强制机械背诵 ID，也不强求每次发回访；重点是对方知道「哪件事」和「真实做到哪一步」。

## 尚未声称完成的事情

- 通用自然语言的所有事实真伪并非靠正则就能证明；当前做的是高置信风险主张、来源和外发链接防线。复杂推断、讽刺、引述仍可能需要更深层语义核验。
- 当前不存在独立、永久的“事实数据库”，而是从真实待办和操作回执**按需形成可验证视图**。这是为了避免同一事实在待办、人生记忆、社交聊天中产生三份互相冲突的数据，也保护遗忘和隐私。
- 真实 B站私信、评论、历史回访账本与 Windows DSH Desktop 的端到端行为仍需用户环境验收。自动测试通过不等于已确认真实账号可发、不会被限流或上下文齐全。

## 验收建议

让同一位好友先提出两个不同请求、让其中一个产生三个子待办并完成，再触发该条回访：收到的文案必须能指认**那条原请求**，且不暴露另一个人的任务；普通私信主动追问不用等回访发出也能读到已完成进度。再次向主人问“你发过视频吗”，鱼鱼不得把选中别人的视频说成自己投稿；向陌生人发送私信不应读到主人私密任务。
