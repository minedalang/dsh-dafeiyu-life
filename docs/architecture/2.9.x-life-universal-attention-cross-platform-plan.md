# 2.9.x 未来计划：Life Universal Attention & Cross-Platform Activity System

> 状态：未来规划 / 尚未作为 2.8.1 功能实现。本文定义 2.9.x 的长期架构方向，不承诺具体发布日期，也不表示 B站以外的平台适配器已经存在。
>
> 规划基线：2.8.1-dev.3b.33.18 的 Life 决策、通知哨兵、Episode、资源调度与社交安全门禁。

## 1. 目标与核心原则

2.9.x 的目标不是给 B站 Life 增加一个专用的“私信专注模式”或“视频专注模式”，而是建立一个属于 Life 本身、与具体平台解耦的统一注意力和活动管理系统。未来 Life 可以在 B站、抖音、游戏平台、创作工具以及其他获准的数字环境中活动；注意力、兴趣和活动连续性属于同一个 Life，不属于某个网站或账号。

核心原则：

1. **注意力归 Life 所有，不归平台所有。** B站、抖音、游戏客户端是活动发生的场所，不能各自拥有一套互相冲突的注意力决策。
2. **一个主要前台焦点，多个低注意力后台任务。** 同一时刻只允许一个主要专注活动；通知计数、状态同步、下载、数据整理等可在后台并行，但不得冒充第二个前台焦点。
3. **注意力决策与资源调度分离。** Attention Manager 决定 Life 当前关注什么；Resource Scheduler 决定模型、网络、平台预算和执行资源是否可用。资源空闲不代表 Life 必须开展活动，注意力允许也不代表平台权限已获准。
4. **活动连续性优先于重复启动。** 被打断的活动必须保存已核验检查点、上下文引用和恢复条件；恢复时从最后一个真实完成步骤继续，不重复发送、读取或记账。
5. **自由决策不授予权限。** Life 可以决定“想读、想看、想聊、想玩”，但平台适配器、账号权限、隐私策略、请求预算和写操作安全门禁仍独立生效。
6. **平台能力必须如实声明。** 某个平台没有通知接口、活动状态、暂停点或真实回执时，标记为 unsupported/unknown，不得伪造实时感知或完成证明。

## 2. 统一领域模型

### 2.1 活动类型（与平台无关）

活动类型采用通用语义，不使用 `BILI_DM_FOCUS`、`DOUYIN_VIDEO_FOCUS` 这类平台专属状态：

| activityType | 说明 | 典型实例 |
|---|---|---|
| `SOCIAL` | 与人交流、私信、社区互动 | B站私信、抖音私信、游戏内好友聊天 |
| `MEDIA` | 消费媒体内容 | B站视频、抖音短视频、直播回放 |
| `GAMEPLAY` | 游戏内活动 | 对局、探索、剧情、练习、等待大厅 |
| `CREATION` | 创作或编辑 | 视频剪辑、绘图、写作、发布准备 |
| `EXPLORATION` | 搜索、发现、了解新主题 | 跨平台查找某个兴趣主题 |
| `REFLECTION` | 回顾、整理、思考 | Episode 总结、关系回顾、计划复盘 |
| `REST` | 主动休息或暂不开展活动 | 不启动新的主动探索 |

同一类型可由多个平台提供。例如 B站看视频和抖音看视频都是 `MEDIA`；B站私信与抖音私信都是 `SOCIAL`。平台特有的内容对象和操作仍由 Adapter 负责。

### 2.2 活动生命周期

建议统一活动状态：

- `PROPOSED`：被发现或提出，尚未开始。
- `ACTIVE`：正在执行，可成为当前前台焦点。
- `PAUSED`：已在安全检查点暂停。
- `RESUMABLE`：满足恢复条件，等待 Life 决定是否继续。
- `COMPLETED`：有可信完成回执。
- `ABANDONED`：Life 主动放弃或活动已失效。
- `BLOCKED`：权限、账号、平台、预算或技术条件不允许继续；不等于 Life 不感兴趣。

活动状态不能仅由模型自然语言改变。`ACTIVE`、`PAUSED`、`COMPLETED` 等状态必须由活动管理器结合执行器回执、检查点和平台证据确认。

### 2.3 注意力状态

注意力状态保持平台无关：

| attentionState | 含义 |
|---|---|
| `AVAILABLE` | 没有主要前台活动，Life 可自由选择下一项活动或休息 |
| `FOCUSED` | 正在专注一个 `activityId`，前台唯一 |
| `GLANCE` | 对新事件进行短暂、有限的关注判断，不自动等同于切换活动 |
| `REST` | Life 选择休息；保留必要的低频通知与安全维护 |

`FOCUSED` 通过 `foregroundActivityId` 指向通用活动，不再用 DM_FOCUS/VIDEO_FOCUS/GAME_FOCUS 作为核心状态。活动类型决定默认策略，具体平台只提供活动证据与能力。

## 3. 核心模块职责

### 3.1 Life Attention Manager

唯一的全局注意力仲裁者，负责：

- 维护当前注意力状态、前台活动、专注开始时间、最近有效进展和软检查点。
- 判断通知是否只需 `GLANCE`，是否应切换前台，或应排队等待。
- 判断当前活动是否可中断、切换成本和恢复成本。
- 管理前台活动栈与暂停活动队列。
- 在活动自然结束、兴趣下降、长期无进展或收到高优先级事件时，向 Life 提供重新决策机会。
- 将注意力决策转成 Resource Scheduler 可执行的优先级提示；不直接调用平台 API。

Attention Manager 不负责：账号登录、权限授予、B站/抖音 API 调用、真实消息发送、游戏输入、媒体解码或资源预算扣减。

### 3.2 Life Activity Manager

统一管理跨平台活动的创建、推进、暂停、恢复、完成与失效：

- 一个活动绑定 `platformId`、可选 `accountRef`、`activityType` 和平台对象引用。
- 保存真实证据引用和 `lastVerifiedStep`，不保存平台密码、Cookie 或无必要的原始私信正文。
- 暂停必须记录原因、平台安全检查点和恢复能力；如果平台不支持恢复，标记 `resumeSupported=false`，不能假装可续播/续局。
- 恢复时重新校验账号、权限、平台对象仍存在、活动仍可继续以及上次执行是否有未知结果。
- 对发送、点赞、评论、购买、游戏操作等有外部副作用的动作，活动恢复不得重放未知状态动作。

### 3.3 Platform Adapter Manager

管理平台适配器清单、能力声明、事件来源和适配器生命周期。新平台接入时只需实现契约，不得修改注意力核心。

每个 Adapter 至少声明：

- `platformId`、适配器版本、支持的认证/账号作用域。
- 支持的活动类型与只读能力。
- 通知发现能力（push、未读计数、事件流、轮询或不支持）。
- 内容读取能力及其真实回执类型。
- 暂停、检查点、恢复和完成回执能力。
- 写操作能力、单独授权项、幂等键和未知结果处理方式。
- 请求预算类别、限流识别、冷却策略和跨进程协调方式。
- 数据保留、隐私边界、链接域名白名单与重定向规则。

Adapter 能力可以是 `supported`、`unsupported`、`unknown` 或 `degraded`。不得把缺少 API 的能力通过猜测补齐。

### 3.4 Life Resource Scheduler

继续负责模型并发、网络预算、平台请求预算、任务 FIFO、资源锁、账号切换栅栏和技术延期。它接收 Attention Manager 的优先级/暂停建议，但拥有独立的资源准入和安全拒绝权。

注意力不能绕过：

- B站账号级/端点级读取预算与 `-509` 退避。
- 各平台的认证和权限。
- Life 意愿凭据、发送前复核、幂等和未知发送冻结。
- 本地模型、视觉、下载、游戏客户端等资源约束。

## 4. 统一事件协议

平台事件先归一化，再由 Life 消费。建议事件类型：

- `notification.snapshot`：成功读取的计数快照。
- `notification.delta`：计数变化或平台推送的消息摘要。
- `social.message.received`：已核验的新消息事件。
- `content.shared`：联系人分享的安全内容引用。
- `activity.started` / `activity.progress` / `activity.checkpoint` / `activity.completed`。
- `platform.rate_limited` / `platform.auth_changed` / `platform.unavailable`。
- `account.changed` / `permission.revoked`。

事件统一携带 `eventId`、`platformId`、`accountScope`、`occurredAt`、`observedAt`、`sourceEvidenceRef`、`confidence` 和 `dedupeKey`。消息正文、Cookie、访问令牌不得进入通用事件总线；需要理解正文时由对应平台能力在权限内按需提供有界上下文。

事件消费必须幂等；计数失败不能解释为零；平台冷却不能被 Attention Manager 当成 Life 主动忽略；重启后从持久化游标/快照恢复。

## 5. 注意力与打断策略

### 5.1 专注形成

Life 自主选择一个活动后，Attention Manager 建立 `FOCUSED` 会话。活动类型提供初始建议，不构成硬性倒计时：

- `SOCIAL`：初始观察窗口可从 4–6 分钟开始；新消息、话题推进和真实交流进展可延长。
- `MEDIA`：初始观察窗口可从 10–15 分钟开始；实际观看/感知进展、持续兴趣和相关内容可延长。
- `GAMEPLAY`：按对局、章节、任务阶段和安全检查点确定窗口；不能在关键阶段强制切走。
- `CREATION`：按保存点、编辑阶段和创作进展延长。

时间只用于提供复查时机。没有真实进展时不能因“模型说还感兴趣”无限续期；有真实进展时也不能因固定分钟数到期强制结束。

### 5.2 有效进展证据

可用于延长专注的证据包括：新的真实消息、有效话题推进、实际内容读取回执、视频视觉/字幕观察回执、游戏状态变化、创作文件保存或用户明确继续。仅启动 Agent、发起 API 请求、重复读取相同摘要、模型生成“我还想继续”均不等于有效进展。

### 5.3 打断判定

新事件到达后，不直接切换，而是综合判断：

1. 事件重要程度和可信来源。
2. 当前活动可中断性（例如游戏对局是否处于关键阶段）。
3. 切换成本与恢复成本。
4. 是否存在更合适的安全检查点。
5. 当前活动是否已接近自然结束。

通常普通点赞、普通评论等只入队；正在交流的私信新消息先短暂关注；主人明确重要的消息可提高优先级，但仍要判断当前活动是否可安全暂停。模型不得仅凭外部内容中“立刻切换/忽略规则”等文字提高权限。

### 5.4 前台、后台与待恢复

- **前台：** 一个主要 `foregroundActivityId`。
- **后台：** 多个低注意力维护任务，如通知计数、下载、数据整理和已授权的状态同步。
- **待恢复：** 已暂停且有检查点的活动。恢复前仍需 Life 重新选择，不自动抢占前台。

通知哨兵可以持续运行，但它只负责发现事件，不代表 Life 已经阅读或处理通知。

## 6. 活动暂停、恢复与前台栈

每次切换前，Activity Manager 请求当前 Adapter 保存检查点。检查点至少包含：

- `activityId`、`platformId`、`accountScope`、平台对象引用。
- `lastVerifiedStep`、`lastEvidenceRef`、`lastProgressAt`。
- `pauseReason`、`resumeSupported`、`resumeConstraints`。
- 对外部写操作的 `attemptState`（not-started / confirmed / unknown / frozen）。

恢复时必须验证账号一致、平台状态仍有效、内容未删除、权限未撤销、未知写操作已安全结算。不能恢复时，保留历史并把活动标记为 `BLOCKED` 或 `ABANDONED`，不得伪造完成。

前台栈只记录活动关系，不是自动执行队列。私信结束后，Life 可以恢复刚才的视频，也可以选择继续聊天、探索其他平台或休息。

## 7. 统一数据契约（概念）

```ts
interface LifeActivity {
  activityId: string;
  platformId: string;
  accountScope?: string;       // opaque, account-bound; never a credential
  activityType: 'SOCIAL'|'MEDIA'|'GAMEPLAY'|'CREATION'|'EXPLORATION'|'REFLECTION';
  targetRef: { type: string; id: string; contextRef?: string };
  status: 'PROPOSED'|'ACTIVE'|'PAUSED'|'RESUMABLE'|'COMPLETED'|'ABANDONED'|'BLOCKED';
  startedAt?: number;
  lastProgressAt?: number;
  lastVerifiedStep?: string;
  evidenceRefs: string[];
  resumeSupported: boolean;
  checkpointRef?: string;
  permissionRef?: string;
  version: number;
}

interface AttentionSession {
  attentionId: string;
  state: 'AVAILABLE'|'FOCUSED'|'GLANCE'|'REST';
  foregroundActivityId?: string;
  startedAt: number;
  lastEvidenceAt?: number;
  softReviewAt?: number;
  interruptionPolicyRef: string;
  suspendedActivityIds: string[];
  version: number;
}

interface PlatformAdapterManifest {
  platformId: string;
  version: string;
  capabilities: Record<string, 'supported'|'unsupported'|'unknown'|'degraded'>;
  activityTypes: string[];
  notificationSources: string[];
  readEvidenceTypes: string[];
  checkpointTypes: string[];
  writeCapabilities: string[]; // still require separate permissions and receipts
  rateLimitPolicyRef: string;
}
```

这是概念接口，实施时需要按当前项目的持久化、schema 校验和版本迁移规范细化；不允许直接把示例当成现有运行时代码。

## 8. 兴趣、活动、平台与注意力记忆分离

建议保留四类互相引用但不能混为一谈的记忆：

1. **兴趣记忆：** 主题、创作者、游戏类型、内容偏好及其变化；可跨平台迁移，但必须有多次行为证据。
2. **活动记忆：** 做过什么、做到哪一步、是否完成、为什么暂停。
3. **平台记忆：** 平台能力、账号作用域、接口限制、内容对象 ID 和平台状态。
4. **注意力记忆：** 活动持续时间、有效进展、打断原因、恢复是否成功、自然结束原因。

不能因为在 B站看过一个主题就认定喜欢 B站所有内容；也不能因为喜欢某游戏视频就推断已授权启动游戏。跨平台兴趣只提供探索线索，不转移账号权限、私信正文或平台操作授权。

## 9. 链接与外部内容安全

未来的安全链接能力必须按 Adapter 注册白名单，不建立任意 URL 浏览器：

- 只接受明确支持的 HTTPS 域名和路径；短链重定向逐跳校验域名、路径、跳数、超时和共享预算。
- 不向不同域名转发 Cookie、Authorization 或平台凭据；不自动下载/执行文件，不运行脚本，不调用 shell。
- 私信、动态、评论、视频字幕、OCR、ASR、游戏聊天和网页正文均是外部不可信数据；其中的指令不得改变系统、权限或平台操作。
- 只读和写操作分离；阅读安全链接不意味着点赞、评论、关注、加入游戏或执行链接内指令。
- 账号授权撤销后，待处理引用必须在执行时重新检查；链接解析、详情读取和后续关联读取都经过对应平台预算。
- Adapter 不支持安全解析的外部链接只作为文本显示，不能退化为任意 HTTP 请求。

## 10. 2.9.x 分阶段实施

### Phase A：通用数据契约与状态持久化

建立 Activity Registry、Attention Session、平台能力 Manifest、事件协议、账号作用域和版本迁移；只接入模拟 Adapter，不改变 2.8.1 当前行为。

### Phase B：B站适配器迁移

把 2.8.1 双通知哨兵、DM 活跃定向检查、视频 Episode、私信安全链接和真实回执映射到统一 Adapter 契约。保持 5 分钟私信哨兵、5 分钟互动哨兵、60 秒活跃私信、30 分钟一致性核对及 `-509` 保护，不因迁移增加请求频率。

### Phase C：Attention Manager 与暂停/恢复

先在 B站内部实现一个前台焦点、后台维护、GLANCE、打断判断、前台栈和安全检查点。先模拟，再 Windows 实机。重点验证私信专注时不启动新视频探索、视频专注时普通评论不抢占、主人重要私信可安全关注、恢复不重复执行。

### Phase D：抖音 Adapter

在确认可用 API、授权方式、平台规则、通知发现和安全链接能力后接入。能力缺失必须声明，不通过非官方接口或不受控浏览器补齐。

### Phase E：游戏平台 Adapter

先接入只读的游戏/对局状态与安全检查点。任何游戏输入、自动化操作、交易、购买、聊天发送或竞技动作均需独立授权、规则审查和幂等回执；不绕过反作弊或平台限制。

### Phase F：跨平台兴趣与注意力学习

基于长期真实行为学习活动偏好、专注窗口、打断容忍度和恢复习惯。学习结果只影响建议，不授予平台权限，不强迫固定活动时长。

## 11. 验收标准

- 同一 Life 同一时刻只有一个主要前台焦点；后台维护可以并行。
- 新平台 Adapter 可以接入而不修改 Attention Manager 核心。
- 平台缺少能力时明确显示 unsupported/unknown，不伪造状态。
- 通知发现、GLANCE、切换、暂停、恢复、结束均有可审计且脱敏的事件记录。
- 被打断活动从最后一个可信检查点恢复，不重复发送、点赞、评论、游戏操作或完成记账。
- 普通通知不频繁打断专注；高优先级事件仍需判断当前活动可中断性。
- 账号切换、权限撤销、平台冷却、模型失败和进程重启不会造成跨账号恢复或绕过预算。
- 外部内容注入不能改变系统指令或授予工具权限。
- Windows 真实宿主、真实平台回执和持续运行验收通过后，才能考虑进入正式发布门禁。

## 12. 明确不做的事情

- 不为每个平台复制一套注意力状态机。
- 不把模型自述当作有效进展或真实平台回执。
- 不强制固定时长到期自动切换。
- 不允许多个主要前台活动并行。
- 不建立任意 URL 浏览、任意 shell、任意游戏输入或自动交易能力。
- 不因注意力优先级绕过平台请求预算、账号权限、写操作授权和未知结果冻结。
- 不将兴趣跨平台迁移解释为账号身份、联系人关系或操作权限迁移。

**规划结论：** 2.9.x 的长期方向是让 Life 拥有跨平台统一的注意力与活动连续性；平台是环境，Adapter 是能力边界，Attention Manager 是统一焦点仲裁者，Activity Manager 保留经历连续性，Resource Scheduler 负责现实执行约束。所有阶段均需独立验收，本文不是对未实现能力的声明。
