# 2.8.1 手动视觉图片验收：Node 宿主启动本地试验

> 仅供本机试验，未证明真实图片识别成功、不得发布为正式修复。

## 已知 Windows 实机事实

- DSH 官方 CLI 的默认/完整配置与视觉 Overlay 都能导出。
- 相同的 Desktop CLI，PowerShell / Node / 原生 Conda Python 发起时成功，视觉虚拟环境 Python 发起时 Node 内部出现 `EPERM`。
- 不隐藏窗口、`CREATE_NO_WINDOW`、`STARTUPINFO` 和清理 Python 环境变量均不改变这个对照。
- 将启动职责交给独立 Node 宿主后，保持同一视觉 Python 的配置合成由 `headless_config_dump_exit` 变为 `headless_patch_composed`。

这是**进程父子关系相关**的故障证据，不证明具体被拒绝的 Windows 系统调用，也不能唯一指向 Defender、ACL 或 DSH 自身。旧路径中 Node 子进程曾启动，并产生 Node 内部 `EPERM` stderr，故不能将其说成 Python `CreateProcess` 本身失败。

## 本轮最小接线

`index.js` 的手动固定图片验收启动一个单次受限本机 Node HTTP 服务；Node 将 256 位随机能力令牌与随机端口**仅通过 Python 子进程环境**传递。`vision_dsh.py` 只有在检测到二者时才将配置导出与固定图片验收请求交给宿主执行，其余情况下保持旧路径。不改生产视频或 Life 视觉调用。

服务严格校验 `DeepSeek Harness.exe`、官方内置 Desktop Host CLI、`headless` profile、来自当前 Duty Home 的 nonce 私有只读图片 Overlay，且仅允许该固定验收提示词。执行通过 Node 原生 `spawn`，`shell:false`，继承项目原来的配置、安全门禁及有限输出。输出只在内存中通过 loopback 返回 Python；Python 原有 MCP 图片 SHA256/字节数/nonce 与模型最终回答、人工认可均保留。

## Windows 验收门槛

1. 完全退出 DSH，安装本地测试包，重启并确认管理中心实际加载的是 `...-hostprobe.1`。
2. AI 模型 → 视觉识别模型：不重新修复健康的 Python，直接运行固定图片验收。
3. 记录 `headlessConfig`、`mcpImage`、`providerApi`、`modelAnswer` 的安全阶段与实际最终回答。
4. 只有人工看见准确对应固定图片的回答，且 nonce 图片回执已核实，才算端到端通过。
5. 若 `headless_config_dump_exit` 仍出现，先核实本地插件版本及 Duty Home `vision_dsh.py` 的受控部署是否已同步。绝不直接禁用完整性校验。

## 边界

本地实验不修复生产视频视觉、Ollama 黑窗，也不会鉴定 Windows `EPERM` 的具体 syscall。试验失败后按交付包提供的回滚说明恢复原插件代码和安装包，不删除 Duty Home 的任何用户数据、凭据、记忆、队列或回执。
