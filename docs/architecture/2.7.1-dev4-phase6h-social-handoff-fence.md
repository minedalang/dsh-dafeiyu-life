# 2.7.1-dev.4 Phase 6h：社交交接跨进程排他基础（未启用 Life 接管）

> **已在旧 DM/评论的所有权 `route()` 中接入持久排他检查；没有启用 Life Agent 社交决策、预约或发送。** Linux 的合成测试不代表 Windows/真实 B站/模型验收通过。保持 `2.7.1-dev.4`。

## 统一层归属、复用与新增理由

`旧已核验 DM / 公开评论 → SocialDecisionOwnership.route → 新 SocialHandoffFence.check →（无预约时）原 legacy 生成及发送闸门 → 原渠道真实回执`。

| 项目 | 唯一职责 | 本阶段不做什么 |
|---|---|---|
| 身份绑定和来源 | 现有 `trustedLifeAccountTag`、`accountBinding`、入站处理器 | 不读取私信正文、昵称、联系人、线程标识 |
| 社交决策授权 | 原 `SocialDecisionOwnership`，仅 legacy | 不根据 Life Agent 模式或影子对照解锁新 owner |
| 交接排他基础 | 新 `lib/social-handoff-fence.mjs`，账号+渠道的**持久、跨进程、匿名**预约 | 不是发送账本、不是 AI 决策本身，也不是原收件游标 |
| 平台发送与回执 | 现有 `SocialPolicyGate`、`SocialInteractionCoordinator`、`dm-send-receipt` 和评论/DM 发送链 | 不承认模型分类是平台回执；不自动补发不确定写入 |
| 审计与可见性 | 原 Life Agent 调度状态接口+管理中心 | 无新增公开诊断 API、无原文、无 UID、无外发按钮 |

现有 `read-action-execution-gate` 只保障 B站只读动作预约，不能直接复用到社交决策交接，否则会把“读取证据”错当“决定发言”的幂等状态。因此新层**仅**承担社交交接生命周期的排他条件；复用原账户绑定和原发信回执。实际两个生产入口（DM/评论）共享 `SocialDecisionOwnership.route`，同样检查这套状态，无重复的两套锁逻辑。

## 真实行为与边界

- 新增目录：`$DSH_HOME/bili-duty/social-handoff-fence/lanes/<SHA256>`（即原 `stateDirOf(ctx)` 下），若宿主自定义 DSH_HOME 以实际状态目录为准。只保存匿名账号作用域哈希、渠道、PID、生成时刻、随机本地 token；**不存**账号明文、UID、消息正文、目标 ID、平台会话、提示词或平台回执。
- `check({channel,expectedScope})` 已接到 `route()`，每次 DM/评论生成与发送仍执行原来的检查。没有预约时完全沿用旧生产逻辑；有该账号该渠道的有效/残留预约时，拒绝旧处理器继续生成/发送，可阻止已处于预约状态的旧调用；**检查本身并不是从检查到发送全程持锁，仍存在检查后开始预约的竞态，因此不能声称已完成原子交接**。另一渠道、另一账号不受影响。原 Phase 4 在 `off` 且账号不可核实时的历史兼容分支未扩大权限。
- `reserve()` 是为下阶段人工或合成流程预留的内部 API：**仅**允许 `legacy` 标志，不能指定 `life-agent`。本阶段任何生产入口都不调用它，所以正常用户不会由于升级自动生成预约。当前没有 `life-agent` 的 `reserve` 许可，也没有接管开关。
- 原子创建目录抢占；中途崩溃、内容缺失、标记不合法、权限异常或符号链接异常时默认冻结。**不能靠 TTL、PID 消失自动删锁**。`releaseDecisionOnly()` 只给持有本进程随机 token 的未发送决策阶段；它不意味着“发信成功”。
- `reviewNoSend()` 必须由运行已停机的独立复核流程，并明确确认完全**未触发平台写入**；活跃 PID、缺失/非法记录、未核实当前账号均拒绝放行。此能力目前只供合成演练，**不在管理 UI 公开一键解锁**。真实发送结果不确定时不能使用“确认未发送”绕过账本核验。
- 状态只显示 `dm/comment` 是否锁定、是否需要复核，不泄露账号或原消息；UI 仍明确“Life Agent 未接管”。旧历史状态、账户配置、原模型额度、个人记忆与备份格式均不迁移。

## 触发、可观察性和五项离线验收

用户正常使用不必执行任何新操作。管理中心 → 鱼鱼想做的事 → Life Agent →「社交回复所有权」可看到：旧回复器仍拥有发送权；跨进程交接预约无阻塞或某渠道阻止；阻止时仅展示渠道，不展示联系人。

```powershell
node .\tools\dev4-phase6h-social-fence-offline.mjs
node --test .\test\v271-dev4-life-agent-phase6h-handoff-fence.test.mjs
```

离线脚本只用系统临时目录、合成账号和真正的子进程，不访问真实安装目录，无 B站连接、没有模型调用、没有对外发送；五场景覆盖跨进程抢占、崩溃残留不自动解锁、跨账号/渠道隔离、伪造授权无效、人工核实后恢复旧路。测试也覆盖异常文件/符号链接、账号切换、过期、预留目录残留、无 UID/私信泄漏。CLI 复核仅存在于测试环境，不提供对真实用户存档的自动修复命令。

### 故障和回归矩阵

| 场景 | 期望 |
|---|---|
| 无预约、账号已核验 | 原私信和评论按原策略运行；新层零模型/网络成本 |
| 某账号某渠道被预约 | `route` 拒绝旧决策和发送；其他渠道/账号仍正常 |
| 崩溃发生在原子目录创建后 | 残留即阻止，不自动按时长释放 |
| 切号、文件异常或符号链接 | 不误认旧锁归新账号；异常 fail-closed |
| 模型要求社交接管 | 内部 API 拒绝 Life Agent requester；无公开开关 |
| 真实 DM/评论/主人 DM/动态/回访 | 前两者仅多做只读检查；其余仍用原发送和回执协议 |
