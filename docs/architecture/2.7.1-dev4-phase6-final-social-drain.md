## 统一层归属与唯一状态源

| 路径 | 权威层 | 本轮新增 | 非职责 |
| --- | --- | --- | --- |
| 生活意愿/模型回复 | 原 `SocialAutonomyDecisionContract`、`InteractionBatcher`、Life Voice | 决策在途登记 | 不替换模型，不强迫回复 |
| 账号/社交 owner | `trustedLifeAccountTag`、`SocialDecisionOwnership.route` | 仍由 legacy 决策，接收交接预检 | 不启用 life-agent requester |
| 交接隔离 | `SocialHandoffFence` | 跨进程 `beginLegacyOperation`、`endLegacyOperation` 与 in-flight 排空检查 | 不保存原文/UID，不作发送回执 |
| 外发与幂等 | 原 `SocialPolicyGate`、原渠道回执 + `SocialSendTransaction` | 可信评论 Agent 返信也进入逐来源事务 | 不用模型回复替代平台成功回执 |
| 管理中心 | 既有 Life Agent 状态接口 | 本账号按 DM/评论显示在途数量、异常残留 | 不给“强制解锁/自动接管”按钮 |

### 正式调用顺序（已接线）

1. 已验证入站后走 `SocialDecisionOwnership.route`（仍只批准 legacy）。
2. 旧生成器进入 `runLegacySocialOperation('decision')`：先原子登记当前账号/渠道的持久在途记录，**再检查**是否存在预约，最后执行模型；`finally` 清理自己的记录。主人评论 Agent 按同一协议覆盖其处理与回复阶段。
3. 旧普通 DM/公开评论（包含 P6 气泡、动态回复）发送前进入 `runLegacySocialOperation('send')`，保留原审批/额度/节奏和前一轮实现的逐来源 `SocialSendTransaction.execute`。
4. 旧主人私信 Agent、待办回访、明确的部分主人操作结果通知、仅入选视频主动分享、暂停状态的回忆私信等路径纳入 **在途发送观察**；这些路径既有发送/回执规则仍不变，其中不少尚未接入逐消息事务，不能据此宣布全域幂等。
5. 额外接线：可信主人/好友评论回复由原 `bili_reply_manual` 取得平台回执，但同一来源+用途先进入共享 `SocialSendTransaction.execute`，没有可信 rpid 不会标记成功。
6. `SocialHandoffFence.reserve`（仍只允许 `legacy` 的内部离线调用）先创建持久排他预约，再检查在途数量。只有 `quiescent:true` 时才证明**该账号/渠道当时已排空已接线的旧路径**；`false` 代表仍有操作或残留，严禁声称可切换。

## 为什么这个协议能关闭旧版竞态窗口

- **旧操作先登记**：即使此前读到“没有预约”，后来的预约也能在已持久化的在途目录中看到它，不会误判为无活动。
- **预约先关闭通道**：即使旧操作刚创建了在途目录，它仍必须再次检查预约；若已关闭，必须拒绝模型/发送。旧操作可能在清理前被预约看到，因此“仍在途”可以保守误报，但不能把正在执行误报为已排空。
- 同账号 DM/评论各自独立，其他账号不共享状态。PID 消失、超时、文件不完整、符号链接、目录联接异常均不能自动宣称排空。
- Windows 不要求用管理员权限跑测试；链接注入测试优先使用 NTFS junction，若 Windows 策略禁止，仅跳过注入案例，同时保留常规非法文件的安全验证。
- 管理中心不展示事件内容、UID、联系人、原始来源键。只展示当前账号的匿名计数。

## 明确未完成（禁止写成正式封版）

- **上线切换前必须停止所有仍在运行的旧代码版本进程，升级所有 JS 发送入口，并确认状态显示没有在途记录**：旧版进程不会登记在途信息，因此不能用新版的零计数证明未升级进程已经退出。
- **Life Agent 没有真实社交决策者身份**。Phase 5 影子仍只能比较 `reply/defer/silent`，不能代替实际回复生成及权限链。尚未实现正式 owner 切换配置、独立联系人授权、逐渠道实机灰度/撤回。
- 在途排空覆盖当前 JS 已接线的旧路径，但不覆盖 Headless Python 中独立操作、主 Session 人工 MCP 操作、所有其他评论/动态写入口。不能称整个 B站产品“唯一发送入口”已达成。
- 部分旧主人命令回复、主动分享、回访尚仅加入在途排空，不具备统一逐消息事务的完整来源身份与真实回执核验；仍必须保留其原有业务去重与审批。
- `social-send-transactions` 的不确定平台发送只能由人工对照 B站结果和原账本处理。**不可**通过 `reviewNoSend`/超时/PID 消失清理尝试过的平台写入。
- Linux 合成验收不代表 Windows/B站。必须完成旧账号/新账号切换、断网、重启、未知结果、真实联系人白名单灰度，且由维护者明确授权后才允许开启真实社交接管。
