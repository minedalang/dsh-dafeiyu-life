# 2.7.1-dev.16 · 视频评论独立回执、动态恢复与 Life 证据（未发布）

## 统一职责与事实源

`LifeWillingness` 继续提供自主意愿；`life-video-action-bridge` 持有短期、当前账号绑定的单动作批准。**原 Python `bili_reply` 是唯一视频评论写入者**，其原 `outbound_reservation`、公开评论每日统一账本、策略和重试冻结完全不变。`video-action-verify.py` 只读平台，返回是否在指定视频评论页观察到原结果；`LifeAgentEvents` 只保存匿名后续考虑，不存原评论、UID、BV、Cookie 或平台 `rpid`。

## 具体数据流与边界

1. Python 视频 MCP 自主评论在工具执行前发送 `BV`、原拟发布正文及是否顶层给本地回环 Life 授权网关；网关不持久化正文，最多暂存 90 秒。每条评论仍独立模型批准，并在写入时再次通过原 Python 额度、防重和授权。
2. 原发送函数返回可信 `rpid_str/rpid` 且报告已受理时，Python 仅把评论 ID 通过回环网关返回。**发送函数的 `success` 不直接作为 Life 完成证据**。
3. 宿主只读 Python 进程核验本账号 Cookie UID；取 `BV→AID` 的单视频公开信息，再按项目现有 `/x/v2/reply/main?type=1&oid=<aid>&mode=2&next=0&ps=20` 查询近期评论；严格核对同一 `rpid`、作者 UID、完整原文，且不能标记不可见。全部匹配后才结算 `verified`。
4. 若评论未进入最近 20 条、API 暂不可用、平台缓存未更新、原文因 @ 插入或图片行为有所变化，结果只能是 `accepted-unverified`，**不能推断没有发送，也不能重发**。此机制不保证 @ 通知送达或永久可见。评论楼中楼由原宿主社交事务管理，不复用此顶层视频 Agent 只读匹配。
5. 对动态仍沿用独立 `dynamic ID + 当前账号 + 完整正文` 严格查验。跨重启若只留下 `publishing` 且没有确定 ID，超过十分钟后标为 `uncertain`，需要离线核查，绝不重新发布；旧 `published` 带 ID 的记录仍可由 `verifyPending()` 在下次 tick 只读重查。旧无账号绑定记录不能擅自确认。
6. `LifeAgentEvents` 对已确认写入继续产生一个、可去重的匿名后续考虑机会；时间线通过行为类别标注「平台只读回查」或「原发送事务」，不存原文字和平台 ID，不直接造成下次发送。

## 与现有策略保持兼容

- 无新增公开评论写入器；**每日公开评论统一默认容量 1000 条不变**，已保存的老用户个性化限制也不修改。
- **视频 Agent 最短启动间隔 20 分钟不变**；生活活跃档不是强制写入或固定日发送次数。
- `bili_reply` 如果没有确切评论 ID，则结果不确定；未知状态原流程冻结，不自动重试。
- 平台只读 GET 可能有延迟、限流、字段变化。**真实 B站账号和 Windows 环境未执行验证**；恢复机制仍不能从完全未知的发送结果自行推算 ID。
- 收藏夹删除仍缺可靠独立平台读回；不能用原工具自报升级可信完成。Life 1.0 长期连续生活与跨日成长因果仍未完成 RC 验收。
