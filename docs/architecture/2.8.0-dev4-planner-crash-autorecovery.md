# 2.8.0-dev.4 · Life 自动恢复调度锁（崩溃恢复 P0）

## 已有实证问题

用户 2026-11-12 的 `/api/bili-duty/autonomous-planner` 回显 `running:true`、`schedulerPulse.lastSkipReason=planner-already-running`、`runLease.held:true`、`ownerAlive:false`、`needsReview:true`，模型退避与额度均未触发。旧版 `autonomous-planner-run.lock` 故障退出后永不自动回收，调度器虽在每分钟检查却无法发起新模型决策。

## 自动恢复与安全闭环

- 入口：`AutonomousPlanner.start()` 开始定时器前进行一次恢复检查；`runLease.acquire()` 在遇到同类占用时再审一次，以涵盖运行中外部数据恢复和旧实例突然退出。
- 范围：**仅** `autonomous-planner-run.lock`（自主规划运行排他租约）。必须有普通目录、唯一的 `owner.json`、合法版本/种类/UUID/PID/时间，以及 `process.kill(pid,0)` 返回 ESRCH，才证明原进程已结束。不能靠锁的年龄判断“超时死锁”。
- 竞争：用额外的原子目录 `autonomous-planner-run-recovery.lock` 串行化多进程修复；每次在守卫内再次检查原锁并将其原子改名隔离，独立核对后才删除。随后重新按原 `mkdir` 原子租约争用；另一个实例已获得新锁时绝不抢走它。
- 失败：仍被活 PID 持有的锁、PID 身份无法判断、符号链接、坏 JSON、异常附加文件、守卫冲突都不解锁；常规活守卫冲突下一分钟自动重看；如果守卫本身已来自退出的进程，则给出 `planner-recovery-guard-orphaned`，保留现场且不冒险删除。未知/损坏状态需留存诊断。异常守卫本身若在修复时再次崩溃且残留，亦将拒绝危险清理，不能保证此类二次损坏无需管理员复核。
- **绝对不恢复**：已入账模型额度不退款；上次异常退出的模型调用、待办、视频能力、评论、私信一律不重放；`life-willingness-ledger.lock` 与原外发事务、未知/已消费证明的冻结都不会清除；事件账本、权限、账号、冷却、备份隔离不变。只有下一轮重新取得可信候选且 Life 重新决定，才可能开展新动作。
- 日常可观测：`runLease.autoRecovery.count/lastAt/lastResult/lastError` 说明本进程自动恢复情况；`schedulerPulse.lastSkipReason` 显示真实阻断原因。管理中心以普通用语提示，不再将持锁当模型退避或主动休息。

## 只读测试与实机边界

`test/v271-dev4-life-agent-atomic-recovery.test.mjs` 包含真实子进程退出与自动接管、两独立实例争抢同一旧锁、一日模型额度保持、未知锁拒绝、旧外发账本隔离。测试不连接 B站，不需要用户手工执行离线工具。

离线测试无法证明所有 Windows 进程退出形式、文件权限问题或网络文件系统中的原子性。旧离线恢复工具只作异常/损坏情况的可选维护工具，**不应再作为正常重启恢复 Life 的前提**。运行锁恢复与旧平台未知事务人工复核属于不同问题。
