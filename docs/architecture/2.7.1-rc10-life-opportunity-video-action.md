# 2.7.1-dev.7 · RC10 Life 机会竞争与视频逐动作意愿（未发布）

> 这是 RC9 完整源码上的实际增量。版本仍为 `2.7.1-dev.7`，`releaseReady=false`，无 Windows/真实 B站发布验收。

## 当前真实架构

1. 生活、DM、评论/@、生活动态、视频分享和视频委派原先已经使用 `LifeWillingness` 合同，但触发器分别调用模型。RC10 **同一宿主进程、同一账号**下 140 ms 内出现的可信行动机会合并为最多 8 个候选，**一次** Life 模型选择，其他机会明确返回 `defer`，不冒充主动沉默。已验证动作后设置 30 秒跨渠道休息。仍共用 `autonomous-planner.json` 的原子模型调用预算，**没有新增机会持久账本**。
2. 新 `lib/life-video-action-bridge.mjs` 在主宿主的 `127.0.0.1` 随机端口提供短期、随机密钥、进程内授权。`index.js` 只给**本轮 headless 视频 Agent overlay**注入地址和密钥；不能获取可用地址时，自动动作拒绝。先复核宿主当前的账号 UID、账号隔离标识、总开关；随后将视频动作提案送到同一 `LifeWillingness`，模型可以行动、沉默或延期。批准票据 90 秒有效，每次外部写入只消耗一个，不能复用。关闭服务器/换账号，待核实动作作未知处理。
3. 原 Python `vendor/bilibili-mcp/mcp_server.py` 的 MCP 工具注册层，对**自主视频点赞、收藏、关注、取关、自建收藏夹删除、视频顶层原创评论**统一加上逐次审批包装器。这个包装器位于工具入口，不依赖提示词自觉；在原有 `_guard`、视频入选来源、权限、单账号日额度、原跨进程预约、平台回执之外加一道门。普通宿主评论回复 `BILI_JS_MCP_ADAPTER=1` 的既有 Life 审批链仍独立使用原发送事务，不重复向视频网关询问。主人手动明确动作另走原手动授权和工具，不受视频自主合同代替。
4. 网关接收 Python 提交的执行结果时，**只记录 `accepted-unverified`（来自 Python 自报）或 `uncertain`**。Python/B站工具中的真实账本仍是唯一写入结果事实源；不把本地授权、模型输出、API 返回自述当成实际观看、公开可见或人格成长证据。
5. RC10 在匿名 `life-decision-traces` 记录当前世界上下文的摘要指纹，允许对照不同日期“提供了不同的可回忆事实 / 最终选择改变了吗”；不会记录完整上下文、私信内容、UID 或模型 prompt。只是**相关性及模拟反事实可测**，不声称真实长期人格成长已得到证明。

## 仍未完成的发布必要条件

- **单一全局永久队列尚不存在**：140ms 内的进程内并发机会才会在同一轮竞争；其他进程、跨时段排队仍靠原生产触发器和账本。若未来需要跨进程长期机会仲裁，必须另做原子持久队列、消息续行与重启恢复；不能仅用此版本的 batch 冒充完整实现。
- **已确认公开回复→动态候选**新增同账号 45 秒去抖唤醒，只在旧授权 `commentSyncDynamic` 开启、原评论真实成功、账号未切换时让现有 `dailyDynamic.tick` 提供一次机会；动态仍需独立 Life 意愿、原配额/隐私/平台回执。**这不是可跨重启恢复的机会队列**，也不允许恢复 Python 旁路直发。
- **Life 主动关心主人**仍受原暂停开关限制；不能为了体现自由而绕过许可或骚扰边界。
- 真实多模态“看见/听见”、真实 B站账号权限、多日人格/兴趣变化、老用户记忆冷恢复、Windows/Anaconda、72h 连续及 7 天观察，必须在实际环境完成。
- `BILI_JS_MCP_ADAPTER` 标志与视频 overlay 属于同一宿主信任边界；并非对能直接任意执行本机 Python/Shell 的攻击者提供操作系统沙箱。不得把 Python 工具包装器宣传为系统级沙箱。
