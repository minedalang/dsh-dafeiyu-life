# 18:22 私信：统一 Life 续办旧消息误触发“新消息到达”

## 证据与故障边界

用户 2026-11-17 18:23:41 导出的本机诊断记录：私信模型已准备两条回复，最终 `p6LastTurn` 保持 `prepared`、`confirmed=0`；当前联系人最近入站结果为 `pre-send-superseded` / `new-message-arrived`，Life 续办存在三条 `review-required` 与三条 `technical-deferred`。这些记录证明回复在发送前受阻，不等同于平台已经发送或 Life 主动沉默。

代码中的旧判定 `!person.seen.includes(messageId)` 只能说明**尚未消费**，不能说明**在模型思考期间新到达**。当普通轮询/可信续办仅处理部分旧消息，而发送前再次读取完整会话时，其他旧消息会被认作新消息，造成反复延期。这是统一续办放大了旧判定缺陷；无法凭该日志断定统一资源调度是全部不回复的唯一原因。

## 变更

- 为每轮将进入 `generateReply` 的消息确定到达边界：记录本轮真实入站消息 ID 与开始时间，兼容 B站秒级时间戳。
- 发送前只把**不属于该轮原始快照、也未曾处理，且时间不早于开始秒**的消息当作真正的新到达；历史积压且时间早于模型开始的消息不会阻断。该边界只存于本轮内存，不持久化私信明文/ID。
- 第一条发送前、后续气泡发送前、模型自然补充回复共用同一判断；平台快照无效则拒绝发送。
- 原有模型选择回复后若发送前检测到新消息，`p6LastTurn` 记为 `superseded`；平台复核失败记为 `technical-deferred`。两者均无平台成功回执，不会标记 delivered。不同账号/权限、手动复核、平台结果未知等原有门禁不变。

## 回归与未完成

新增合成场景：单联系人六条积压（3 人工复核/3 技术延期），两条计划回复成功通过发送前旧消息校验；真正新消息（含同秒新 ID）继续拦截；首条已确认后第二条期间有新消息则停止第二条；平台返回非数组 fail-closed。仅本地适配器模拟成功，并不证明 B站真实外发成功。

风险：如果平台/本机时间显著不同步，基于本轮到达时间的判定可能需要额外隔离处理。现阶段不能降低发送权限或跳过二次网络核验。用户 Windows 实机需验证新私信被确认送达，历史 `review-required` 不自动补发，`-509` 恢复仍维持原退避。
