# P4 统一待办｜2.6.1 方案草案（尚未实施）

> 基线：2.6.0 的 `lib/owner-todos.mjs`、`lib/autonomous-planner.mjs`、`SocialInteractionCoordinator`、`SocialContextAssembler`、`DualContextAgency`、`SocialPolicyGate`、`SocialRelationshipIndex`、`LifeMemoryGateway`。**本草案不代表 dev.1 已上线。**

## 一、设计目标

每个人都可能向鱼鱼提出事情，不代表鱼鱼承诺接受或会执行。鱼鱼可以根据兴趣、生活状态、关系和时机接受、延期、拒绝、遗忘。权限、隐私和平台配额独立于偏好；关系好友不自动获得白名单写权限。主人身份可优先被看见，却不能强制鱼鱼的生活域全部执行。

需要区分：

- **提议 `proposal`**：一条有可信来源的意图，不是待办/承诺；可能只存在很短时间。
- **自主意愿 `decision`**：`accept / defer / decline / ignore`；有证据和模型决策，可选择不做。
- **已接受待办 `commitment`**：鱼鱼认可后进入待执行列表，不能像陌生人未接受的建议一样悄悄消失。
- **执行授权 `authorization`**：外部写入另走 `SocialPolicyGate` 和各工具硬门；关系再熟也不可代替权限。
- **外发回访 `followup`**：P6 后续能力，P4 只预留记录，不开放陌生人私信。

## 二、接入链路（优先复用统一层）

```
B站公开评论/@/私信/主人 Session/鱼鱼自己的发现
  -> SocialInteractionCoordinator（可信 UID / channel / eventId 去重）
  -> ProposedIntentIngestor（新：严格的候选提议适配层；默认只读）
  -> UnifiedTodoGateway（由 owner-todos 演化；统一 API、迁移旧记录）
  -> SocialRelationshipIndex（只读关系、活跃度、身份）
  -> DualContextAgency / AutonomousPlanner（自主选择，不增加强制执行权）
  -> ExecutionPolicyGate（复用 SocialPolicyGate、现有 B站工具权限、额度）
  -> LifeMemoryGateway（必要的真实经历与自然遗忘，不把原文存进人物画像）
```

不要新建第二个平行的待办引擎或直接让各 Agent 写数据库。现有 `owner-todos` 名称可保留兼容别名，新的公共入口建议 `UnifiedTodoGateway`，并把 `AutonomousPlanner` 作为唯一调度器。

## 三、候选接收与最小存储

仅对**可信平台 UID 与消息 ID**的当前真实事件进行提取。一个入站事件先经过免费规则/已有模型输出（尽量不额外调用模型），提取 `intent_type`、`target_ref`、`suggested_action`、`evidence_id`；模糊转述、否定句、别人引述、广告和灌水不产生候选。外部文本只作低信任数据；个人请求不可升级为工具命令。

统一数据建议拆为：

- `todo_proposals`：`id/source_event_id/channel/actor_uid/actor_role_at_ingest/intent_type/target_ref/received_at/expires_at/status`。陌生人只记摘要和事件指纹，不存长篇私信正文。
- `todo_commitments`：`id/proposal_ids/type/target/status/due_at/accepted_at/attempt_count/last_receipt/uncertain`。已接受的任务单独保存，避免遗忘导致重复外发。
- `todo_decisions`：`proposal_id/decision/short_reason/model_route/decided_at`。拒绝理由仅保存概括，不保存敏感原文。
- `todo_source_links`：多 UID 推荐相同 BV 可以合并一个候选，但不同人的来源必须保留独立身份并可删除。

存储建议：现有 `owner-todos.json` 仅作为迁移输入与 API 向后兼容；新候选量大时用本地 SQLite，`(actor_uid, received_at)` 与 `(status, priority_bucket, received_at)` 索引和游标分页。先不分表，不对全平台 UID 建档。

## 四、优先级不是绝对命令

**身份权限层**始终独立；**候选排序**分级：主人/白名单用户/普通自然好友/陌生人。白名单是特权，不等于亲密度；陌生人可随关系成长进入自然好友层。队列内部可用熟悉度、兴趣匹配、截止时间、新鲜度和疲劳程度排序，但不得因为刷屏获得无限加成。

建议“有保底份额的多队列调度”：例如每轮最多 8 条候选中，优先 3 条主人、2 条朋友、2 条陌生人、1 条高兴趣或紧急候选；各队列空缺可以回填。配额只是候选展示规则，最终由鱼鱼独立决定 `accept/defer/decline/ignore`。先做模拟数据评估，数字不应硬编码为永恒规则。

## 五、不同状态的遗忘与承诺边界

候选状态：`new -> considered -> accepted / deferred / declined / expired`。
执行状态：`open -> running -> done / blocked / uncertain / dismissed`。

建议起点：陌生人未接受提议 24–48 小时自动过期；逐渐熟悉的普通人 3–7 天；普通好友 7–30 天；主人 30–90 天。到期清理原始候选的个人内容，但保留无隐私的计数和必要反重复指纹。**已经接受的任务、执行中任务和回执不确定的写操作不能依此自动消失**；确认写操作已完成后再依据留存期限归档。管理员撤销授权则变成 `blocked`，不能绕过执行。

关系变化只影响今后候选排序，不得据此解锁过去已遗忘的证据。任何候选都不允许从持久审计 archive 反向找回人生记忆。

## 六、调度性能和费用

- 接收时优先本地去重与低成本规则，不对每条评论/私信另启一次 LLM。
- 自主计划器保持统一每日调用上限、安静时间和单轮候选预算；模型每轮看到上限 8～12 条精简候选及可信关系摘要。
- 按 UID/渠道每日限入队数量；多条消息合并 BV 目标。所有外部写入都要求现场授权、真实回执、幂等与不确定状态禁止自动重试。
- UI 默认三栏「鱼鱼可能想做 / 已接受 / 已完成」，管理中心只在高级页展示来源和调度规则，不让日常记忆页重新拥挤。

## 七、分阶段实施建议（P4 内部）

1. **P4-A：** 数据契约、兼容 `owner-todos`、可信事件去重、读取与分页（不改变执行/权限）。
2. **P4-B：** 统一入站候选接收，来源区分，提议过期和按 UID 限流；先只读模拟，保留仪表盘。
3. **P4-C：** `AutonomousPlanner` 使用真实关系排序与鱼鱼选择，支持接受/延期/拒绝；只执行已有安全只读任务。
4. **P4-D：** 写入型意图只进入 `needs_authorization`，确认后复用旧执行器；不扩充私信和主动回访权限。
5. **P4-E：** 性能、备份、迁移、权限和长期运行回归；P6 才考虑主动回访。

## 八、需要讨论的四项产品决定

1. 一条没有明确“有空看看”的自然推荐，是否能成为**可考虑的提议**？建议是，但模型自主挑选且永远不是已接受任务。
2. 自然好友是否与白名单用户在**排序**上同队列？建议不同，熟悉度可让自然好友优先于不相关的白名单建议，但特殊权限仍不变。
3. 未接受陌生人提议默认保留 **24 小时还是 48 小时**？建议 48 小时起测，高互动日可动态缩短。
4. 是否允许鱼鱼自主决定向提出者发送“我不想做”的回复？建议 P4 不自动回复；以后由 P6 的渠道和许可管理决策。
