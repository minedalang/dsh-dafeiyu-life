# 2.8.1-dev.3b.33.9：统一资源协调与自然生活线索收敛

> **开发版、实现范围与未验收边界（2026-11-17）**：本文件描述代码行为，不是 Windows、真实 B站或 DSH 模型视觉验收报告。上一篇 [dev.3b.33.8 全系统审计](2.8.1-dev3b338-system-integration-audit.md) 是本改造的审计依据。仍禁止云端全量测试、实际账号发送、npm 发布。

## 1. 决策与排队的不同职责

- **Life 认知和意愿**：`autonomous-planner` 从可信消息、真实回执、可续 Episode 和生活契机里选择是否行动、忽略或休息。队列调度器**不能**制造意愿、替 Life 批准评论、私信、点赞或强制视频选择。
- **账户隔离的 Life 事件箱**：`life-agent-events` 的人工/社交/定时提示只是供考虑的候选，不是必须执行的任务。本轮只合并重复的合成提示，绝不合并可信的不同 DM、评论消息。
- **Life Resource Scheduler**：`lib/life-resource-scheduler.mjs` 是**单宿主进程内**可观察的短租约资源仲裁器；不会持久化消息、不储存提示词，不接管跨进程写入凭据，也不是跨进程全局队列。
- **专业执行器**：原 DM、评论、视频、动态、记忆各自执行、保留自身合法权限和持久化队列；Life 原意愿、`life-willingness-admission`、DM 结果未知冻结及平台回执是强制约束。

## 2. 四条队列与四类资源

| 工作种类 | lane | 允许的资源仲裁 | 边界 |
| --- | --- | --- | --- |
| 私信及评论相关模型、B站读取 | `social` | `model` / `biliRead` | 先等资源，再经过原账号/权限/-509/次数验证；只保证决策机会，不强制发送 |
| Life 已开始的短阶段及画面观察 | `continuation` | `model` / `vision` | 长 Episode 应逐阶段释放；看到画面仍必须有可核验模型视觉回执 |
| Life 公开候选读取、视频子进程启动 | `exploration` | `biliRead` / `video` | 视频轮次用非等待槽位；被占用只能延期，不可假装启动成功 |
| 记忆与反思模型 | `background` | `model` | 低负载执行，不得压过已排队的社交任务 |

单账号通过 16 字节十六进制 Life tag 核实；切换后**排队旧任务不能开始**。资源默认 `model=1, biliRead=1, video=1, vision=1`，互不阻挡，不是全局串行。按社会/续行/探索/后台权重 4/3/2/1 和每 15 秒等待老化排序，连续最多两次优先社交，防止后台永久挨饿。**已经运行的动作不抢占**；平台未知写入必须继续冻结。没有“紧急就绕过 -509”的通道。

`model` 接入 `index.js` 的社交/规划与部分记忆模型入口；`biliRead` 接入主 JS MCP 只读适配器及 `lib/dm.mjs` 的会话读取入口。**DSH Headless 子进程内部的独立 Python MCP/模型/FFmpeg 调用不全部经过本进程模型与读取槽位**：其原有预算和安全 overlay 继续有效，尚不能宣称“全球共享所有 API 资源”。`video` 控制 JS 宿主发起的长视频子进程的并发启动，`vision` 控制 Life 画面观察入口，不会共享同一个阻塞队列。更完整的跨进程资源协调需要后续 IPC/账户级持久租约和 Windows 实机验证。

## 3. 生活契机自然化：真实事件不应被合成闹钟淹没

- 同账号同时最多保留**一个待 Life 处理的 `quiet-window`**；重启读取旧账本时合并重复窗口，关闭多余旧提示，不把它们当作 Life 自主忽略。
- `experience-ready` 是已核验经历的**后续考虑提示**，不是一次真实新事件。待办提示最多留 3 个，防止反馈回环无限堆积；不同真实 DM、评论事件不受此上限影响。入选后续仍由 Life 选择继续或停止。
- 已达 `episodeSteps >= episodeMaxSteps` 的 Episode 不进入规划候选/`resume_episode` 菜单，且保留原选择后执行时的身份、步骤和来源检查；不能仅在提示词里提醒模型。
- 同账号、同 BV 的**公开元数据**读取最多 40 秒成功缓存及在途合并，必须先通过每位请求者的原动作授权；平台读取预算冷却时不使用缓存绕过 -509。私聊、图片、评论、用户资料及平台写入**不缓存**。
- Life 的 `skip` / `休息` / `延期` 是有效自主选择。模型忙导致的 `resource-deferred` 是技术延期，不得消耗实际模型调用额度，也不得变成 Provider 退避或虚假的自主沉默。只有被调度器拒绝、明确**没有启动模型回调**的请求可以退回当天的调用额度；真实模型执行失败和发送未知状态**绝不退款或重试发送**。

## 4. 运行状态与体验验收

`/api/bili-duty/life-agent/integration-status` 增加 `resourceCoordination` 的纯数量状态；管理中心仅展示资源槽位、每条 lane 排队数、技术延期数量。`/api/bili-duty/autonomous-planner` 增加 `lifeResourceCoordination` 状态。统计不记录原消息/聊天文本、真实 UID、BV、Prompt、密钥或任务地址。只读状态不代替平台写入账本。

受控增量应验证：连续社交优先后非社交必得机会、已运行视频不被打断、账号切换无跨账号续办、待办超时不生成自主拒绝、`-509`/共享预算不被缓存绕过、合成 quiet-window 多日积压收敛、Episode 步数上限、真正模型出错不退还已使用额度。Windows 应再运行 72h 多场景，在安全前提下核查排队分布、DM 恢复、重复 BV 比例与休息行为的真实前因；本轮**没有**在云端执行这项实机验收。

## 5. 保持未关闭的验收问题

- Windows DSH 图片：只有受限 MCP 的图片 nonce 回执及实际模型最终回答才能认可；当前修复阶段不宣布成功。
- Life 私信：`dev.3b.33.8` 的公平准入与 `dm-life-inbox` 可靠续办仍待 Windows 真实拥塞恢复验收；本轮新增只是资源**排队前置**，不可替代持久送达确认。
- 自然性评价：多日日志已有真实候选筛选、跳过及重复合成唤醒证据；合并机制能降低无谓打扰，但还需要继续监测跨日同主题重复观看和“选择理由”是否真正受到前一轮经历影响。
