> 状态：开发补丁，基于上一次交付的 `2.7.1-dev.6` 完整源码。未获得 Windows 与真实 B站验收；不改变旧社交决策权归属。报告：<https://github.com/minedalang/dsh-dafeiyu-life/issues/9>。

## 真实生产入口与数据流

1. 手动工具、视频 Agent 和后台评论回复均复用内置 `vendor/bilibili-mcp/mcp_server.py` 的 `bili_reply`。收到明确 `success: true` 才进入 `_comment_result`；无回执、失败、超时不生成成功评论记录、不自动重发。
2. 唯一公开评论主账本继续是账号现有 `seen.md`（以及原月度 `seen/YYYY-MM.md` 归档）。`_record_comment_in_ledger` 原先执行 `safe_line(text,20)`，使真实评论在写入时不可逆截断。新记录最多保存 4096 字符的实际发送文字（剔除行分隔符、转义表格竖线）。旧记录不补造正文。
3. 只有收到**明确成功回执**、并且带图返回 `meme_image.status=submitted_unverified` 与经验证的名称，才在同一 BV+自身 rpid 行增加 `meme_image_name=... | meme_status=submitted_unverified` 字段。不是图片公开可见的证明；工具原有 `meme-diagnostics` 仍仅用于状态诊断，不能当成新的评论真值数据库。
4. `lib/recent-comments.mjs` 从同一评论行读取正文、附图名称和提交状态，统一返回 `/api/bili-duty/recent-comments`。旧 5 列与回复接收人列仍兼容；无效图片路径不返回；归档重复回执优先保留更完整正文。管理中心和会话标签「大肥鱼足迹」都读取此 API，不拼装新来源。
5. 两处 UI 图片展示调用现有 `/api/bili-duty/stickers/file?name=...`，该接口通过 `getCommentMemePreview` 在本地安全图库查找；图片可能已被删除，不能将本地预览描述为 B站 现场截图。所有 UI 通过 `textContent`/React 文本渲染，不注入 HTML。
6. `bili_reply` 顶层 @ 必须受**既有用户设置与名单**限制。UID 非空的名单成员（包括主人）在确实准备 @ 时通过 B站 只读 `get_user_info()` 核验平台用户名。用户在主人资料中写的昵称只用于 AI 选择和排除草稿中的 `@别名`，不再当作平台用户名；失败时省略该 @、继续检查原公开评论授权。不因相同昵称或“主人”角色备注生成目标 UID，也不能以此获得新写权限。

## 兼容、安全及限制

- `seen.md` 仍是**公开发布正文**事实记录；不要把私信正文写进去。4096 字符仅为本地保存上限，用户原评论提示仍通常限制 150 字。
- 老数据里仅存的前 20 字不可从账本恢复，已删除的图库文件无法还原图片；无法凭成功 API 回执证明评论或配图已公开可见。
- `meme_image_name` 是本地图库名称而非服务器绝对路径。没有相匹配的本地文件时界面仅展示记录的名称和回执状态。
- 不新增评论发布次数、发送通道、社交所有权开关或模型调用；Life Agent 的 `socialDecisionOwner` 仍为 `legacy`。下一步正式交接需单独进行分渠道事务复核、实机验证和人工回滚演练。
- 仍需 Windows、真实 B站 @ UID 映射／图片显示、跨账号历史数据与长期监控验收。
