# 2.7.1-dev.4 Phase 4：社交决策所有权显式契约与离线验收

> **当前生产接线，不等于社交 Life Agent 接管。** 代码已接入；本地 Linux + Node 22 离线验证。Windows、真实 B站、真实模型、用户旧数据备份恢复仍待实机验收。基线：已交付 Phase 3 的 `2.7.1-dev.4`。

## 为什么先做这一步

Phase 2 已核验私信、评论可产生匿名生活唤醒；Phase 3 可在短期时间线观察意愿和真实结果。**但旧私信/评论回复器仍独立决策并发送**。`lifeAgentMode=active` 仅代表**视频生活驱动接管**，绝非社交回复所有权转交。若在没有排他规则时再增加一个 Life Agent 社交发送器，同一消息有被两个主体处理的风险。

本阶段先在现有入口提供明确的**决策所有权检查与诊断**，暂不允许任何模型、配置字符串或事件唤醒擅自把社交回复所有权转给 Life Agent。这样下一阶段可以先开发影子上下文读取和只读决策对照，而不要求用户去 B站发消息验收。

## 统一层归属与真实接线

| 入口 | 当前唯一真实状态／执行者 | 本阶段增加 | 权限、隐私及失败策略 | 对应回归 |
|---|---|---|---|---|
| `dm-autoreply` 的 `onIncoming` | 原私信收件游标／`SocialInteractionCoordinator` | 已核验匿名事件交给 `life-agent-events` 后，更新本进程摘要观察值 | 不存正文/UID/原事件 ID；观察不授予社交权限 | `v271-dev4-life-agent-social-wakes`、Phase 4 |
| `comment-interact` 的 `onIncoming` | 原公开评论/动态来源核验和关系投影 | 与 DM 共用观察归属契约 | 仅平台核验合格才计入；匿名短期计数非平台回执 | 同上 |
| 私信与评论 `generateReply` | 原 `interactionBatcher` + 既有社交意愿/权限 | 生成前后核对当前账号与明确的 `legacy` 所有权 | `active` 不会创建新社交决策主体；异步切号不得继续生成旧账号回复 | Phase 4 + 原 DM/评论回归 |
| 私信与公开评论/动态 `send` | 原 `cadenceSend`、渠道发送适配器、平台回执 | 进入发送和节奏等待后，均再核对账号身份 | 不改变原有发送许可／额度／去重；检查不通过停止 | Phase 4 + 原发送回执回归 |
| 主人专属评论 `ownerCommentAgent.accept` | 原可信 @/回复处理逻辑 | 接收前检查当前 `legacy` 所有权 | 不替代其身份与防重规则；不得被新 Agent 再接管 | Phase 4 静态接线回归 |
| 管理中心 | `/api/bili-duty/autonomous-planner` 原只读聚合接口 | 附带 `socialDecisionOwnership` 和「社交回复所有权」一行 | 只展示模式、决策负责人、短期按通道汇总，不展示联系人和原文 | HTML/JS 静态回归 |

新增 `lib/social-decision-ownership.mjs` 是 **运行时决策归属契约**，不是第二份社交事件/权限/关系/发送账本。`route({channel, requester, expectedScope})` 仅批准 `legacy`，Life Agent 任何所有权请求均以 `social-handoff-not-enabled` 拒绝。`observe` 的去重哈希只留进程内最多 400 项/24 小时，不持久化，重启后自然清零；不是跨进程锁，也不能替代平台发送事务与回执门禁。

当前直接负责社交写入的其它独立流程（主动分享、待办回访、主人专用 DM、Python 视频 Agent 的评论／关注／动态）**本阶段没有接管，也没有被本契约全面覆盖**。它们仍须遵守已有社交安全闸、平台作用域与回执机制。不得把此阶段描述为“全站只剩一个外发代理”。

## 用户可观察行为

- `off`：只保留旧社交流程，不增加 Life Agent 社交唤醒；原 `legacy` 决策兼容。
- `shadow`：可获得匿名社交唤醒、时间线；私信/评论回复仍由旧发送器决策，不新增对外发送。
- `active`：有界的视频 Agent 生活驱动可接管；**社交仍为 `legacy`**。不能因为 active 就额外私信或评论。
- 当前账号无可信作用域、或 AI 生成过程中发生切号：`shadow/active` 下拒绝继续这次后台私信/评论决策或发送；不根据旧账号推断新账号。

UI 路径：管理中心 → 鱼鱼想做的事 → 自主待办调度设置 → Life Agent →「社交回复所有权」。新状态只统计本进程核验入站事件，不等于平台消息数或回执数。

## 无需 B站的模拟验收工具

在项目根目录执行：

```powershell
node .\tools\dev4-phase4-offline-acceptance.mjs
node --test .\test\v271-dev4-life-agent-phase4-ownership.test.mjs
```

模拟器只在操作系统临时目录创建 **合成消息/账号/角色身份/待办**，先验证假私信与假评论、跨账号隔离、非法接管，再跑 Phase 3 的冷快照、完整性校验、恢复后冻结。结束后删除整个合成目录；**不会连接 B站、调用真实模型、读你安装的 `$DSH_HOME`、发任何外部消息，也不会消耗 Token**。输出 `ok: true`、5 个通过场景、`externalMessagesSent: 0`、`realBilibiliTested: false` 才算通过这项离线模拟；其它结果应附原始终端输出。

## Windows 与旧数据验收门禁

1. **第一步（现在可以做）：** 应用当前阶段的增量 Patch，执行上述本机模拟与专项。即使未登录 B站也可跑。应当 5/5 场景、7/7 Node 测试通过。
2. **第二步（安装插件之后）：** 在管理中心查看「社交回复所有权」一行；在 `off/shadow/active` 之间观察标题与提示是否一致。`active` 不能显示“社交已接管”。不必给真人发消息。此步骤要重启插件，旧数据请先完成原有安全备份。
3. **第三步（单独验收，不用在这次合成模拟中执行）：** Phase 3 的 Windows 停机冷快照+`verify`，先在独立测试目录恢复并检查 `restore-freeze`。正式数据不得直接恢复覆盖，也不得把完整快照发给开发者。
4. **真实社交写入只会在下一阶段拿到用户明确指定的可控收件人/目标后进行；** 目前完全没有要求在 B站操作。

## 向下一阶段的过渡（尚未实现）
