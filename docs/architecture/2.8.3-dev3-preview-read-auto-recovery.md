# 2.8.3-dev.3 · 只读视频取帧预约自动恢复（当前源码实现）

> 范围：仅 `bili_preview_frames` 这一只读取帧动作；不改变 B站外发锁、Life 自主意愿、视频证据真实性、分盘与遗忘规则。属于 dev.3 增量维护，不提前推进 dev.4。

## 两种独立生命周期

1. **B站预览帧读取**：现有 Python/Node 跨进程持久预约与统一平台预算继续生效；Python `independent_local` 的 `analyze_perception` 在完成 B站取帧、构造真实帧证据后，触发受限 `before_model` 回调，由同一个 Python 工作线程结算读取预算、验证账号并释放预约。
2. **Ollama 识图**：只有取帧阶段成功释放后才开始视觉推理；模型超时、失败或等待不再占用该次 B站帧读取预约。最终视觉回执仍按实际 `analyzed`、`cached`、`vision_incomplete` 或失败状态独立核验。

## 遗留的 `executing` 预约

- 只有在**同一受信账号作用域**、锁记录完整可信、动作确属 `bili_preview_frames`、原预约已存在至少 30 分钟且宿主操作系统**明确证明原 PID 已结束**时，才允许自动归档 `auto-recovered-unverified`，然后移除旧锁。不会调用 B站，不会补写成功证据，也不恢复旧任务执行。
- Python 和 Node 共享文件协议：恢复前通过 `recovery.claim` 的独占创建进行竞争保护；完成前复核原记录和 PID，先写独立受限审计回执，再删除精确的旧锁。任何权限错误、未知 PID、仍活着的持有者、无效/链接文件、账号不匹配、并发失败都保持阻塞。
- 只有**新的**、本来就被授权/选中的只读调用，在旧锁安全结束后才可能执行；自动恢复本身绝不触发新的读取。跨账号、字幕、评论、私信及外发事务一概不走此特例。
- 普通用户管理页仅显示执行、恢复或安全隔离状态，已移除手动解锁按钮。开发者紧急 API 仍保留原安全检查，但额外要求宿主进程显式设置 `DSH_DEV_READ_ACTION_UNLOCK=1`，不能成为用户的必需步骤。

## 未改变、仍需验收的边界

- 已在运行且仍持有锁的旧版 Python 进程不能被新代码强行释放；先让旧进程真正退出。证据不够时程序只隔离、不冒险重复读取。
- 本地主人视频 Debug 已采用仅允许 `bili_preview_vision` 的一次性 Python MCP 进程：调用总时限为 7 分钟（含 Python 初始化和工具响应），随后请求关闭该专用进程；外层 8 分钟界面兜底不再遮蔽最后一个已确认阶段。无法确认退出时仍按原有安全规则隔离。DSH 独立视觉模式及其它共享任务没有被强制取消。
- 本地单次 MCP 进程通过 stderr 仅上报固定阶段码（进程启动、等待预约、取帧、取帧结算、Ollama 推理、工具返回）；只在 owner Debug 显式开启，不记录 BV、模型正文或凭据。这只能定位最后已确认阶段，不能断言该阶段的具体故障根因。
- Windows/macOS/Linux 真实进程退出、Ollama 长时间推理和可能仍存活的外部子进程仍须实机验证。
- 本轮开发环境的模拟测试不等于 Windows/macOS/Linux 的 DSH+Ollama 实机测试；未触碰用户个人数据、没有访问真实 B站，也没有执行手动解锁。

## 统一层归属

- 事实来源：`read-action-executions/locks` 的同账号预约及受限 `receipts`；未新增另一套队列、任务身份或写授权。
- 权限来源：现有已核验账号及只读工具白名单；恢复不授权任何新读取。
- 生命周期：平台读取、模型分析分段；过期不是充分条件，进程明确退出才可回收。
- 失败语义：无平台成功回执时只能记为 `auto-recovered-unverified`；模型识图成功另走视觉证据验收。
- 架构接线未变：本轮未改动四张 Life Mermaid 图。
