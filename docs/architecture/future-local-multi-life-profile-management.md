# 大肥鱼 Life · 本地多记忆档案管理器详细设计方案

> 文档类型：未来版本架构提案 / 讨论稿；**未实施**，不代表 2.8.2-dev.11 已有多档案能力。  
> 核对基线：用户此前提供的最新源码，累计至 `2.8.2-dev.11` 的独立回放副本。  
> 设计目标：**一台 DSH 实例可本地管理多份相互隔离的 Life 记忆，但同时只能运行一份；不同电脑可各自运行独立记忆。** 不建设在线账号、同步服务或商业云功能。  
> 关系：不替代《通用分层记忆与渐进式回忆初步方案》；这是**多份 Life 的容器、身份与生命周期管理**，前者是**单份 Life 内的记忆组织与回忆机制**。亦不提前实现桌宠开放平台的真实 API。

## 1. 先确认的产品语义

1. **档案不是 B 站账号。** 一份档案代表一只具有连续经历的鱼鱼；该鱼鱼可先后使用不同 B 站账号。相同 B 站 UID 被多个档案配置过，也不会合并两份记忆。
2. **档案不是普通备份。** 档案是可选择、可运行、会继续成长的生命状态集合；备份是某个时点的只读恢复材料，不会被视为另一只正在运行的鱼鱼。
3. **每个档案拥有不可变的唯一 ID，昵称只用于展示。** ID 不由昵称、文件夹名、电脑名称、B 站 UID 或 Cookie 推导；昵称修改不改变人格与记忆事实。
4. **每台 DSH 实例一次只激活一份档案。** 其余档案处于休眠，绝不参与记忆检索、后台提醒、模型上下文、B 站读取与发送。
5. **不同电脑可以各自运行不同档案。** 完全离线时不能技术性证明“同一 ID 从未在其他电脑运行”；对同一档案跨电脑搬迁采用主动移交和冲突提示，未来在线租约另做。
6. **记忆归记忆，授权归授权。** 换档案需要重新核实当前档案的主人授权、B 站凭据、好友白名单、社交边界。上一档案的熟人和行为许可不能自动转移。
7. **不能通过档案复制/恢复绕过遗忘。** 旧快照不能在正常读记忆、备份索引或衍生缓存中偷偷把已遗忘的内容放回来；离线持有旧导出文件的使用者仍有恢复可能，产品必须明确说明限制。

## 2. 当前实现及为什么不能只复制文件夹

以 `2.8.2-dev.11` 为核对基线：

- `lib/state.mjs` 中的 `stateDirOf(ctx)` 将插件数据定位到 `$DSH_HOME/bili-duty/`；`index.js` 启动时马上以该路径初始化配置、凭据、记忆、账号和多个业务模块。目前没有「档案选择先于全部模块启动」的总闸门。
- `lib/account-binding.mjs` 已有 `character-identity.json` 的稳定 UUID、`account-binding.json` 的角色/账号绑定验证、每账号运行态和切号冻结。**应复用此身份，不应另建第二套可漂移的“灵魂 ID”。**
- `lib/life-memory-gateway.mjs` 的 `life-memory/episodic.json` 与事件补偿、档案及反思/兴趣等只是整体状态的部分。另有长期记忆、人格情绪、关系索引、待办、授权配置、回执、SQLite、Python 运行端等。
- `lib/data-backup.mjs` 当前便携式备份有显式白名单与敏感排除：B 站登录凭据、部分私密好友观察、外部插件数据等不包含在普通导出中。因此「普通备份导入＝完整转移一只鱼」在现阶段不成立。
- 现有 `docs/architecture/future-life-account-relationship-continuity.md` 区分鱼鱼认识旧友与新账号是否被对方认出；多档案必须继续遵守该边界。

**设计结论：新能力的最高层归属应是 `LifeProfileManager`（档案定位、激活、互斥、导入/导出和目录管理）；档案内部事实仍由既有 LifeMemoryGateway、长期记忆、账号绑定和授权模块拥有。绝不将 ProfileManager 做成第二个记忆数据库。**

## 3. 统一概念、ID 与状态

| 概念 | 建议字段 | 意义 | 是否可改 |
| --- | --- | --- | --- |
| 本地档案标识 / Life 身份 | `profileId` | **直接复用**当前 `character-identity.json.id` 的 UUID；所有索引、迁移引用它 | 永不修改 |
| 昵称 | `displayName` | 如「主世界鱼鱼」「蓝蓝的试验人生」；允许重名，但 UI 同时显示短 ID | 可改 |
| 本地说明 | `description` | 用户填写的识别备注，不注入人格模型 | 可改 |
| 可选图标 | `avatarTheme` | 本地预设图标/颜色，仅 UI 外观 | 可改 |
| 档案状态 | `idle / active / pending-switch / quarantined / archived` | 休眠、运行、待切换、受保护、归档 | 系统维护 |
| 创建设备提示 | `originDeviceHint` | 人类可读的本地标签，不作为身份凭据 | 可改，不可鉴权 |
| 上次运行 | `lastActivatedAt` | 本地时间，供档案列表展示 | 系统维护 |
| 备份信息 | `lastVerifiedExportAt`, `lastVerifiedBackupAt` | 成功核验的时间与摘要 | 系统维护 |
| 来源 / 分叉 | `lineage` | `created`、`imported`、未来 `forked-from` | 只读审计 |
| 本地管理序号 | `generation` | 防止 UI 缓存/旧进程写到已切换档案 | 严格单调增加 |

**不建议增加一个与 `character-identity.id` 不同的“memoryUuid”。** 用户所说「每份记忆的唯一标识」可直接对应 `profileId`，避免角色 ID 与记忆 ID 冲突。单条记忆仍保留现有 `memoryId`，如 Life 情节 ID；两者职责不同。

昵称建议限制为 1–32 个可见字符，去除控制字符、路径分隔和脚本格式内容；不可用昵称当目录路径、鉴权凭据或导出文件唯一键。界面可显示 `9d13e7b2…` 等短 ID，但技术操作永远使用完整 UUID。

## 4. 推荐的本地目录结构（方案，不是现有目录）

```text
$DSH_HOME/bili-duty/
├─ profile-registry.json           # 仅存可展示的档案索引与 activeProfileId
├─ profile-control/               # 运行锁、切换事务日志；不存聊天原文
├─ host/                          # Python/模型路径、宿主级 UI 偏好、通用脚本等
├─ profiles/
│  ├─ <uuid-A>/
│  │  ├─ character-identity.json   # id = profileId，沿用原角色身份
│  │  ├─ account-binding.json      # A 档案的 B站账号关联
│  │  ├─ config.json               # A 档案专属人格与授权配置（拆分后）
│  │  ├─ life-memory/              # A 的情节、反思、待补偿事件及遗忘边界
│  │  ├─ long-term-memory/         # A 的现有长期记忆
│  │  ├─ accounts/                 # A 的 B站账号级运行态
│  │  └─ ...                       # A 的兴趣、关系、待办、回执、SQLite 等
│  └─ <uuid-B>/
│     └─ ...
└─ exports/                        # 用户指定目录优先；不是运行源，也不扫描为记忆
```

**关键隔离规则：** 索引只列 `profileId`、昵称、状态、时间、格式版本、可选描述，不包含任何私信正文、好友 UID、原始记忆、Cookie、Token、人物画像。`activeProfileId` 只是一条本机激活指针，不是记忆权威来源。所有读写必须经一次已经完成的档案选择，不能默认回落到其他目录。

**迁移策略：** 不能立刻将 `stateDirOf()` 改成根据指针返回任意目录。应先审计 `index.js`、MCP/Python、全局配置、外部插件、备份、日志、模型文件等对旧绝对路径的依赖，然后在启动**最早阶段**完成 `hostDataDir` 与 `activeProfileDir` 的划分。绝不通过符号链接切换旧根目录，也不允许两个档案共享可写 SQLite、事件队列或回执账本。

## 5. 用户可见的「记忆管理」页面

建议导航：**「角色与系统 → 记忆档案」**。主要交互分两层：

**档案列表（只展示轻量元信息，不预加载记忆正文）**

| 示例昵称 | 短 ID | 状态 | 上次使用 | 可操作项 |
| --- | --- | --- | --- | --- |
| 鱼鱼·主世界 | `9d13e7b2…` | 正在运行 | 今天 | 详情、改名、备份、结束运行 |
| 蓝蓝·实验生活 | `4a89ac01…` | 已休眠 | 昨天 | 启动、改名、导出、归档 |
| 旅行鱼鱼 | `01dbb321…` | 已归档 | 上月 | 查看详情、验证归档、恢复 |

详情页分三个标签：**档案信息**（创建时间、UUID、容量、兼容版本、备份状态）；**生活概览**（仅来自本档案现有 MemoryGateway 的安全摘要，不能读被遗忘的归档原文）；**数据与安全**（导出、校验、修复提示、停用、删除）。

**必要按钮与明确反馈：**

1. `创建全新记忆`：设置昵称 → 生成新 UUID → 建立干净档案 → 默认不开 B站社交授权 → 选择是否现在启动。
2. `切换到这份记忆`：先展示「当前运行会结束、未完成任务会被冻结、需要重启并复核账号授权」→ 用户确认 → 安全停止 → 原子切换 → 重启后验证成功。
3. `重命名`：只改展示索引，不改 UUID、角色内容和模型人格。
4. `导出档案`：导出具明确模式的封包，并在完成内容核验后给出结果；不自动联网。
5. `从文件导入`：校验格式和 UUID；遇到相同 ID **禁止静默覆盖**；需选择恢复已有档案或放弃。
6. `归档`：必须先停止运行；归档后不可被自动调度，默认仍保留文件；可再激活。
7. `删除`：不能删除活跃档案；先完成备份提示，双重明确确认（昵称＋短 ID），展示是否删除本机备份（默认不删除），删除失败保留隔离状态；绝不可顺带删除其他档案。
8. `检测完整性`：只读检查文件清单、版本、关键文件结构、必要 SQLite 校验和上次操作日志；检测不应重写记忆。

**避免误导用户：** 不放「一键融合两个鱼鱼」「一键继承另一个账号的全部好友」「设备云同步已开启」等按钮。默认也不允许直接在后台同时激活第二个档案。

## 6. 同一时间只运行一份：本地互斥与事务式切换

**本机约束：** 一套 DSH Home 的同一个 ProfileManager 只允许一个 `activeProfileId` 和一个占有主运行锁的 Life 实例。休眠档案绝不执行 timer、后台批处理、私信轮询、反思、SQLite 写入和模型调用。

建议采用安全的本地租约而不是只有 UI 禁用：

- 首次启动取得 `profile-control/active.lock` 的原子独占创建权（Windows 与 POSIX 都要做单独验收）；内容包含 `profileId`、PID、宿主实例标识、随机启动代次及启动时刻。**PID 单独相同不等于同一进程**。
- 异常锁/损坏锁/可疑符号链接/无法验证的旧持有者一律 **拒绝激活**。不得仅凭锁超时就覆盖；仅当系统能核实旧进程已经不存在且没有未决外发，才走受控恢复。
- 所有持久化与执行门禁绑定当次 `profileId + activeGeneration`。Python/MCP 子进程不得只依赖脚本所在目录猜测当前身份；切换后旧 generation 的回调/写入拒绝。
- 生命周期统一为 `idle → preparing → active → quiescing → idle`；出现不确定状态则为 `quarantined`，不能假装已停止。

**建议切换顺序：**

```text
使用者选择档案 B
  ↓
确认当前 A 的风险与待办
  ↓
阻止新外发/新任务；等待已有安全操作结束
  ↓
冻结未知回执、待确认发送和旧账号待办；冲刷事件与 SQLite
  ↓
关闭轮询器/模型任务/MCP 子进程，释放 A 的所有写句柄
  ↓
校验 B 的身份、数据格式、权限及完整性
  ↓
先落盘可恢复的切换事务，再原子更新 activeProfileId / generation
  ↓
重启 DSH Life → 再核验身份并读取 B；未通过则进入安全隔离
  ↓
显示“当前运行 B”，不自动恢复旧外发任务
```

**不要尝试热切换。** 现有代码启动时有大量闭包绑定、计时器、SQLite 连接与复制到 Home 的 Python 脚本。第一阶段采用**停止并重启 DSH 插件**的保守方案，等单元、跨进程和 Windows 实机检查成熟之后再评估热切换。

**崩溃恢复：** 事务状态持久化记录 `fromId / toId / generation / stage / initiatedAt`。重启时如果上次停在「未验证切换」，不猜测已完成，也不根据文件存在就重跑未确认外发；进入只读修复页，由主人选择重试验证或回滚激活指针。回滚不能撤销已经发生的 B站行为。

## 7. 记忆、账号、关系和主人授权如何隔离

| 数据 | 作用域 | 新建档案时 |
| --- | --- | --- |
| Life 角色 UUID、人格、兴趣、情绪、生活经历、长期记忆 | **单一档案** | 全新、为空或官方默认初始值 |
| B站登录凭据、绑定历史、账号专属待办和读取额度 | **档案内的账号作用域** | 不复制凭据，先登录并核验 |
| 原始私信、私密领悟和社交观察 | **档案＋具体来源账号＋隐私规则** | 不共享，也不因同 UID 放宽 |
| 好友昵称、历史认识/熟悉度 | **该档案内的真实来源** | 不导入其他档案的关系事实 |
| 好友白名单、主动联系允许、授权主人 | **档案内明确配置＋当前账号复核** | 默认安全关闭，必须单独确认 |
| `LifeMemoryGateway` 的可衰减记忆、遗忘状态与证据引用 | **单一档案内统一记忆事实** | 不从另一份档案的归档重建 |
| Python、FFmpeg 安装目录及纯技术 UI 偏好 | **本机宿主** | 可复用，但不代表记忆共享 |
| 运行日志、崩溃转储 | **本机诊断**，附档案短 ID 且脱敏 | 不进入记忆召回 |

换 A/B 档案，不等于换 B站账号；而在 A 档案内 A→B 的 B站换号，也不等于换 Life 主体。两个维度在 UI 和存储中应明确分开。

**特别风险：** 当前 `config.json` 混有宿主技术项与档案的人设/社交授权。拆目录时应维护明确的「字段归属清单」，逐项检查默认值、旧版配置迁移和管理员授权，防止新档案继承上一档案的主人或私信白名单。

## 8. 本地备份、导出、导入与跨电脑移交

必须区分三种操作：

| 操作 | 用途 | Identity | 原始私密数据 | 自动继续待办 |
| --- | --- | --- | --- | --- |
| **普通备份** | 日常安全备份、用户查看历史 | 保持当前档案 ID | 依现有脱敏规则，可排除 | 绝不自动 |
| **完整离线移交包（未来新增）** | A 电脑迁到 B 电脑继续同一份 Life | **保持同一 UUID** | 可选本地加密、由主人显式选择；不得把明文凭据带走 | 绝不自动，需冷恢复核验 |
| **分叉新 Life（以后再评估）** | 从现有经历衍生另一个独立生命 | **必须新 UUID**，留下明确来源 | 仅复制获准的数据，标注来源 | 绝不自动继承 |

建议第一期只实现「全新创建、多份休眠、切换、普通备份、受控导入恢复」；**完整跨机移交和分叉新 Life 必须在真实文件清单、安全迁移与回执冻结完成后单独开发验收**。

完整移交包至少要包含 `profileId`、格式版本、导出时间、来源运行代次、清单、各文件摘要、已知缺失项、业务数据快照（SQLite 用安全备份 API），并将「没有带走」的项目在用户界面列出。SHA-256 可发现偶发损坏，但**单独校验和不提供恶意篡改真实性**；如果以后导出敏感私密经历，应采用成熟密码库的加密封包与密码 KDF，不自创加密算法。

绝不默认导出 B站 Cookie、授权密钥、操作系统秘钥及未经许可的私人原文。若用户需要原样搬移高敏数据，必须另设风险可见、密码保护及端到端验收流程；普通备份不能冒充完整移交。

### 跨电脑案例

- **A 电脑运行记忆 `X`，B 电脑运行记忆 `Y`**：完全允许。两份 ID 独立，本地互不影响。日后可将任一休眠档案导入另一台电脑统一管理。
- **A 的 `X` 导出后，B 要继续运行 `X`**：在 A 上明确停止并导出移交 → B 导入并校验 UUID → B 仅在 A 已停止的前提下激活；A 仍保留休眠副本或只读历史备份。
- **A 与 B 离线同时运行同一个 `X`**：本地无法跨电脑感知，也无法可靠合并两个并行增长的事实库。禁止无提示双向覆盖；检测到移交代次/血缘冲突时标为 `diverged`，让用户保留两个副本并选择处理，**第一期不做自动合并**。
- **一份导出被导入三次**：相同 UUID 被识别为同一身份，不能自动创建三个“不同的鱼鱼”。需要明确恢复、只读备份或以后受控分叉。

## 9. 遗忘、恢复与删除语义

1. “删除一条记忆”和“删除整份档案”是不同操作。前者必须沿用现有 Gateway 的遗忘机制，后者是使用者明确执行的本地数据管理操作。
2. **只读档案管理索引不得包含可用于复原遗忘内容的摘要。** 昵称/容量/最后运行时间不应成为第二套记忆事实库。
3. 正常恢复之前，对比当前档案的遗忘/撤销边界与快照的时期。任何可能复活遗忘内容的旧快照必须阻断普通恢复，改为有明确风险提示、冷恢复流程并保留审计；不能悄悄读取旧归档以补足记忆。
4. 设计未来的低敏“已遗忘 ID / 撤销版本标记”及恢复代次，原则是单调生效、与内容分离。但**无法保证用户手上已经离线保存的旧明文备份被远程删除**；这一限制必须明说。
5. 整份档案删除要先停运行、撤销本地计划任务、关闭文件句柄、清除本地凭据和缓存；具体备份目录不会在默认操作中被自动清除，避免误删其他鱼鱼。
6. 不把删除后的 UUID 重新用于全新记忆；即使同昵称，也应生成新的 ID。

## 10. 未来云同步的预留（**本阶段绝不实施**）

预留最小字段即可：`profileId`、`schemaVersion`、`exportGeneration`、`lineage`、`lastVerifiedSnapshotDigest`、`originDeviceHint`。不要在本地规划版中加入服务器地址、联网探针、账号注册、支付逻辑、赞助墙、云 Token 或后台上传。

未来如以自建服务器、可选商用赞助方式提供服务，需要**另外**设计并征得用户同意：端到端加密、服务端看不到原始记忆、设备授权与撤销、隐私政策、数据导出/彻底删除、付费与赞助边界、存储配额、公平使用、数据迁移、灾难恢复、离线租约冲突以及停服后本地可继续使用。

云端只能协助同步与租约仲裁，**不能成为第二个决定鱼鱼人格与记忆事实的权威**。用户即使停止赞助，也应能本地使用自己的档案；不能用云订阅锁住本地既有记忆。

## 12. 必须新增的安全回归与实机验收

- 新用户创建 `X`、`Y`：UUID 不同；X 的私人经历、兴趣、好友、待办在 Y 中全部不可见。
- `X → Y → X`：X 的人格与未遗忘记忆仍在；Y 的外发请求、账号绑定与授权不会污染 X。
- 同一 B站 UID 分别登录 X、Y：不发生记忆合并，不继承旧好友或自动社交许可；同机并发不能绕过全局锁。
- 同名不同 ID 与改名：都能正常管理，昵称碰撞不影响身份或目录。
- 旧版单档案导入：character UUID 保持，迁移回滚和日志可验证；断电、杀进程、权限拒绝、缺失文件、损坏 SQLite 时停止且不覆盖旧数据。
- Windows 两个 DSH 进程竞争同一 Home；PID 重用、残留锁、锁损坏、时钟回拨、符号链接/目录联接点：拒绝不安全激活。
- 切换中有待发送私信/评论及未知回执：旧任务冻结，下一档案不能重试；回切后仍按原安全门禁判断。
- 子进程 / 模型异步回调在切换后完成：旧代次所有写入被拒绝，日志只记录脱敏原因。
- 普通备份缺少敏感数据时 UI 明确提示；导入不能声称「完整人生已迁移」。
- 两电脑导入同一 ID：不悄悄合并或覆盖；离线并行变化检测到冲突后只读隔离。
- 删除档案不会删除其他 UUID 目录、共享 Python 环境或用户的异地备份。
- 遗忘后导入旧备份不会静默重新曝光已忘记的细节。
- 正式发布前必须执行维护者 Windows 普通/管理员全量测试和实际 DSH 两账号、两档案、两进程、两电脑验收；离线专项通过不等于正式发布可用。

## 13. 我建议默认的用户体验决策

1. **新安装：** 自动有一份「我的鱼鱼」档案，旧用户升级时沿用原 `character-identity.id`；不凭空生成第二只鱼。
2. **新建：** 默认是完全空白、独立的鱼鱼；不做「复制人格」「继承全部好友」；可输入昵称与描述。
3. **切换：** 只在主人主动确认后发生；切换前停止新动作，后续重启激活；不自动发公开动态或私信。
4. **运行规则：** 同一 DSH 实例只有一份活跃；其他档案可管理元信息和导出已校验快照，但不能在后台模拟生活。
5. **离线跨设备：** 允许 A 跑 X、B 跑 Y；同一 X 的 A→B 使用冷移交，不支持默默双开、自动合并。
6. **兼容顺序：** 先确保旧用户数据一个字不丢，再谈新建第二份；所有迁移必须支持中断恢复和明确回滚。
7. **云服务：** 只预留 ID、版本与移交代次；云同步、收费/赞助、SDK 接口、第三方托管均不进入本地首期。

**最终原则：一个档案＝一段独立的人生；一个 UUID＝一只鱼鱼的连续身份；一个实例＝同一时刻只陪伴其中一只。备份用于保护，迁移用于搬家，分叉用于未来明确创造另一只，不能把这三件事混为一谈。**
