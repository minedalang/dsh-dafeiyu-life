# 2.8.1-dev.3b.30 — Windows 视觉故障调查与受控修复

## 证据（2026-11-16，北京时间）

- 源码版本：2.8.1-dev.3b.29。
- 15:39:51.753–15:39:53.143 的可见伪控制台窗口 PID 23340、16260、50008，进程启动事件分别归属 `llama-server.exe`、`llama-server.exe`、`ollama.exe`，共同父进程 Ollama daemon PID 43384。出现窗口前同样有多次 `python.exe` 与 `ffmpeg.exe` 启动，但本组三次可见窗口**不属于** FFmpeg。
- 15:40:49.430 的 `_diagnostics/dsh-vision-selftest-last-run.json`：独立 MCP 预检 ready、MCP 图片回执 not_received、Provider not_confirmed、模型回答 not_returned，DSH CLI exit=1，stderrKind=node_exception，Node 错误码 unknown。不能由此认定模型不支持图片。
- `index.js` 的常规 DSH Agent `spawn` 带 `ELECTRON_RUN_AS_NODE`，而图片验收 `index.js → pyEnv → vision_dsh.py → subprocess.run` 缺少这一步。生产视频视觉 MCP 链路原来也没有显式通过其专用 overlay 环境设置标志。此不一致是**已确认的源码缺陷**，但没有原始安全 Node 错误栈无法唯一证明它就是 exit=1 的全部原因。

## 修复边界

1. `index.js` 手动 DSH 固定图片验收按实际 DSH 启动环境计算 Electron Node 标志，显式传给受控 Python 子进程。
2. `index.js` 视频模型 MCP 只读服务 overlay 按 `process.versions.electron || vdsh.env.ELECTRON_RUN_AS_NODE` 同步标志。`vision_dsh.py` 两条嵌套 DSH CLI 路径使用同一辅助函数，只在标志 `1` 时转为 `ELECTRON_RUN_AS_NODE=1`。
3. 不修改用户的 Provider、API Key、Headless 配置、能力声明与图片人工认可规则；`subprocess.run` 仍然 `shell=False`、固定时限、隐藏 Windows 进程。
4. Ollama 黑窗归属已明确；本版不谎称插件可以控制 Ollama 的内部 `llama-server.exe` 创建方式。新增用户可在本机执行的只读错误类别摘要，以排查为何同一秒内连续创建 runner。

## Windows 验收

- 升级插件、完整重启 DeepSeek Harness，使临时 MCP/vision_dsh.py 运行时代码重建。
- 在“AI 模型 / 视觉识别模型”执行 Headless 图片实测；要求独立 MCP ready、**DSH 实际取得固定图片回执**、收到模型自由回答，再由用户人工认可。若仍异常，用本次新日志的持久化诊断对照错误码；不要自动认可。
- 用 `tools\diagnose-ollama-runner.bat` 只读汇总 `%LOCALAPPDATA%\Ollama\server.log` 与 `app.log` 最近若干行的已知错误计数。没有错误计数不能证明服务没有故障。Ollama 黑窗是否还出现须重新采样，不改用户系统级 Ollama 设置。

## 远程无法证明的事情

无法在 Linux 容器运行本机 `DeepSeek Harness.exe`、Ollama Windows daemon 或第三方 Provider 真实图片输入。专项模拟测试通过不等于实机已经修复。
