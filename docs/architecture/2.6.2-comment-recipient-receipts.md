# 2.6.2 · 公开回复接收人回执（当前实现）

本文件描述**当前源码**的“回复对象是谁”链路，不是架构提案。

## 数据源与校验契约

- 唯一成功发送主账本仍是 `$BILI_DUTY_HOME/seen.md` 及其月度归档。旧记录只有 BV、发送后 rpid、根评论 ID、时间和摘要。
- 底层 `bili_reply`（含 Headless、宿主和主 Session 手动评论）对楼中楼回复使用实际 B站视频 AID 和目标 `rpid` **只读核实**原评论的 UID、昵称与正文。`root` 仅用于定位线程，不能冒充被回复的人；找不到目标则身份保持未知，并不修改已有的发送决策。
- 只有平台确认外发成功并返回出站 rpid，才把 `recipient_uid`、`recipient_name`、`recipient_comment` 附加到主账本当前行；不会从模型生成文本、评论摘要或未验证楼层猜测 UID，也不会因为读取失败重发。
- `lib/recent-comments.mjs` 使用同一键 `(BV, 出站 rpid)` 合并主账本中的平台校验身份、当前账号 `accounts/<UID>/runtime` 下的确认发送索引，以及必要的旧根目录确认索引。如果同一出站 ID 出现不同 UID，拒绝显示身份。
- 管理中心 `/recent-comments` 在宿主内部传入**当前账号**的 `accountRuntimeDir`；不得遍历其他账号目录。不存在凭据核验结果的历史五列记录不自动补写身份，以免将别的评论作者错当接收人。
- 这只是公开评论对象的展示补充，不会创建评论、不修改 `seen.md` 判重语义、不授予互动权限，不替代成功回执或公开可见性复核。

## 故障与兼容

- 如果 B站暂时无法读取目标评论，仍允许已有授权逻辑自行决定是否发送；接收人字段空白不意味着没有发出成功回执。后台会明确显示“旧回执缺少身份，或平台核验未成功”。
- 旧五列行继续可读。已保存在当前账号 runtime 的确认索引可以立即恢复显示；只有旧行、没有可验证 UID 的记录不能凭昵称或楼层做自动补录。
- 账号切换时，只查询当前账号 runtime 和精确出站评论记录；不会遍历其他账号的私信或关系账本。

## 回归要求

覆盖主账本平台字段、旧五列兼容、账号 runtime 与根目录分离、精确 BV/出站 rpid 绑定、楼中楼核验的目标作者而非根作者、UID 冲突拒绝显示，以及 Python 失败/未知回执不写入身份。对应 `test/v262-public-reply-recipient-ledger.test.mjs` 与 `test/test_v262_verified_comment_recipient.py`。
