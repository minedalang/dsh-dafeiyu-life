## 用户日志与可确认事实

用户在 2026-11-06 17:14:32–17:14:38 的手动唤醒 `4431309e` 记录中，Life Agent 成功从 `cues=2` 等可信候选中选择 `begin_exploration`；模型调用与执行前核验成功，但 `bili_video_info` 返回 `metadata-api-error`，结算为 `metadata-read-failed`。**这不能归因于鱼鱼不想行动**，也不能在无平台原始回执的情况下认定 B站具体错误是 -412、-101 或网络超时。旧错误码过于泛化：Python MCP 适配器异常会变成未结构化 `isError`，上层无法稳定区分。

## 诊断协议（无原始异常文本）

Python 视频详情读取异常时只返回类似：

```json
{"ok":false,"failureCode":"metadata-rate-limited","diagnosticOrigin":"python-bili-video-info","failureLayer":"platform","platformCode":-412}
```

其中 `platformCode` 只接受有限长度的有符号非零整数；异常说明、请求 URL、头部和凭据全部丢弃。无法安全还原平台码时为 `0`，上层不展示。无法分类的失败保留 `metadata-api-error`，但 `origin/layer` 标记它来自 Python、MCP 传输、预约或结果格式核验。旧版 FastMCP/平台异常文本仍保守回退到既有失败分类；**不会反推旧日志不存在的错误证据**。保留 `metadata-bvid-mismatch` 和 `metadata-title-missing` 严格拒绝、三次独立探索读失败冷却和平台风控冷却。

**冷却必须真实生效：** 新的 Python 枚举错误同时经过现有 `classifyReadFailure` 和 `biliReadBudget`，`metadata-rate-limited` 被归到 `platform-rate-limit` 并按原退避规则阻止后续平台读取；`metadata-account-unavailable` 触发既有登录态 15 分钟冷却。不得只在 UI 显示错误却继续循环调用 B站。冷却写入原 `bili-read-budget.json`，重启仍有效，**不会**清空旧账本或另建平台额度源。`metadata-read-busy` 明确保留预约占用分类，返回格式非法不被算作成功。


Python 视频详情对 `stat`、`owner`、`tag`、`pages` 中缺失或非预期值做类型安全处理；B站确实没有返回视频 BV 和标题时绝不生成伪造成功。

## 真实验收步骤

1. 应用基线精确的增量补丁，重启 DSH；若 MCP 已被用户修改，不能静默覆盖，管理中心的 MCP 修复要先备份并人工确认。
2. 在「运行诊断 → 鱼鱼的决策全过程」使用「诊断一次真实视频资料读取（不调用模型）」，只点击一次；它只会挑当前账号已有可信公开观察中的一条 BV，不接受外部提供的新目标。
3. 查看显示的「错误类别、来源、层、平台码」。如提示账号未就绪先检查登录和绑定；如 -412 先停止高频请求、检查平台风控；如预约占用先核验锁，不手动强制解锁。
4. 若探测核验成功，再使用「现在让鱼鱼考虑一次」查看模型是否选择以及下一轮 `exploration-ready/use_capability`，真实视频观看与时间线仍需独立平台回执验收。
5. 如显示通用 `metadata-api-error`，应保留新的 `origin/layer` 信息供下轮定位；无平台日志时不能保证原因已找到。
