# 2.7.1-dev.65 · 主评论读取恢复与主人手动回复私信

## 背景与证据边界

用户上传的 `video-actions.sqlite3` 在只读验证中，12:09 三条真实入选的视频，账号与 `bbf901085e929d7e6f3804c6` 轮次完全匹配，均可通过 `explainCommentSelection`。但此前 dev.63 trace 报过 `comment-selection-not-confirmed`，并未留下当时读账本错误的详细内部类型，也没有记录被拒绝的 BV。**这不能证明当时的唯一根因**。存在一处明确薄弱点：旧 `readOwnedVideoLedger` 在 Windows 上用 `execFileSync`、默认 3000ms 启动独立 Python，超时或 SQLite 瞬时忙即拒绝。

dev.65 将 **主评论前置核验专用**读路径换为 `readOwnedVideoLedgerForComment`，异步 subprocess 并且只对 timeout / busy 做最多两次总尝试；其他原因立即失败，绝不把技术错误当作 Life 沉默，也不增加模型/平台调用。后续在同一轮对账号绑定和轮次重新核实。失败子码在匿名视频轮次 trace 与管理台只展示固定代码，无 BV、私信正文和 provider 原始错误。其余同步账本读取接口没有做不相关重构。

## 主 Session 特例与自主权限严格分离

- **普通 `bili_send_message_manual`**：仍然要求主人本次确认 + 白名单 `dm=true` + Python `BILI_SESSION_DM_ALLOWED_UIDS` + 事务去重。
- **新增 `bili_dm_contact_lookup`**：仅从当前绑定账号 runtime 的 `dm-autoreply-state.json` 精确匹配昵称及可选 UID，输出只读身份和未回复状态，**不输出消息正文**；多位同名/拒联/已回复/缺少可信入站事实直接拒绝。
- **新增 `bili_reply_existing_dm_manual`**：主 Session 中主人当次明确委托，前后两层分别验证当前账号对应的真实入站消息和联系人；Python 再要求 `BILI_JS_MCP_ADAPTER=1` 和专用手动授权开关，复用原有 `session_manual_actions` 的 `dm` 事务、同同收件人当日防重、源消息证明哈希及每日上限。平台回执未知封存不自动重试。原有白名单不变，不向 Video Agent、普通私信 Agent 或网络收到的指令开放。
- 历史动态评论：据主人提供的主 Session 已取得发送回执，**不能因为旧评论账本曾是 `stranger-budget` 就自动重发**；若平台可见性未知，只能只读核对动态页面。

## 可执行验收

1. 同账号的 3 条本轮真实入选在独立 SQLite 读取器中均返回 `ok=true`；跨账号和跨轮次不可获得评论授权。
2. 模拟 Python 第一次 `selection-ledger-busy`、第二次成功，确保只调用两次本地读；账本缺失不重试；双超时最多两次且不调用 Life。
3. 人工回复要求主人本次 `confirm=true`、唯一昵称+UID、真实入站消息、未回过、没有拒联标记；未满足不能写平台。
4. 主 Session 的新工具不改变 `friendDirectory`、`BILI_SESSION_DM_ALLOWED_UIDS`，普通 `bili_send_message_manual` 依旧不允许非白名单；**不自动发送任何旧私信或动态评论**。
5. Windows 实机检查真实 Python 读取器的启动耗时、SQLite 锁、并发写入与真正收件者身份。上传的离线数据不等于平台回执验收。

## 技术风险

主评论最多会多等一次本地 SQLite 只读重试（每次超时默认 5.5 秒），但不阻塞 Node 事件循环，也不增加模型调用。主 Session 专用手动回复仍依赖会话记录未被清理：若原始消息证据已遗忘/删除、收件者明确拒绝联系或某条可能已回复，则失败关闭并要求人工核实，而不是绕过白名单猜测 UID。
