## 为什么需要闭环

旧实现允许回复生成与待办结果分离：模型说“记下”却没有给有效 `accept`/`suggestedTodo`，或者数据库没有成功写入，公开评论仍可能照发。原始 JSON 并未持久化，不能对历史那次 `319132990017` 的模型结构字段作确定断言。

`dev.8` 不根据评论是否包含特定推荐关键词就强制建单；由**唯一社交模型**决定是否接受，并附对应用户原话证据；程序只验证来源、近 24 小时有效性、主题/BV证据、只读类型及账本持久化回执。每条候选仍走同一核验器，多个候选有基于主题的稳定幂等键，防止重复轮询重复建单。

如果出现**回复声称已经记下但没有完整可信入账**，或**DM 回复与已经核验的视频资料/待办进度冲突**，程序不替换为固定句子：最多额外调用一次**同一个模型/同一 Life Voice**，提供当轮有限回执让它自行改口、重新提供可核验的待办提案或选择沉默。再次不一致时**停止这轮外发**，不使用任何程序编写的“客服式”替代回复。发送仍须原评论/DM 权限和真实平台回执；待办成功并不意味着评论成功发送。

旧版 DM 纠错模板导出只为第三方兼容保留，实际社交生产路径不再调用它们。其余更广泛的自然语言声称真假判断仍有边界：现行 `SocialTodoReplyContract` 是**保守的明确入账承诺检测**，不是可保证识别所有中文同义句的通用语义判真模型；真实端仍需人工观察误报/漏报。

## 无正文诊断、运行结果与故障策略

管理中心「鱼鱼想做的事」复用原本**本进程最近 30 项**社交待办诊断：`disposition`、创建/重复数量、是否全部落盘、失败类别，以及 `model-revised` / `suppressed-unverified` 状态。诊断不额外保存模型原始 JSON、私信/评论正文、目标 UID、完整主题或鉴权凭据；重启后历史诊断不会延续。真实待办依旧由原业务备份/恢复管理。

发生网络或数据库持久化失败时不自动重新尝试远端写入；存在部分完成时保留已核实项目并报告未完成，不用补写其他不可信主题来“圆话”。项目在发送前依赖成功回执，评论/DM 的真正发出状态仍按原渠道确认。人工补救应从经过登录账号核验的管理页确认账本与原评论，而不是猜测那次模型 JSON。

## 跨渠道回归矩阵

| 场景 | 生产边界 |
| --- | --- |
| 已核验普通公开评论 / 已开启的 @ | AI 独立决定是否接受，可同轮 1–3 个只读待办；无明确证据不得创建；发送仍走公开门禁/回执 |
| DM 陌生人 / 白名单 / 主人 | 仅在原私信收件与授权条件满足时识别；已核验发送者才可进入意愿/待办；私密消息不带入其他 UID 的公开回复 |
| 相同数字但不同平台或 UID | 不使用昵称/数字跨平台关联；原事件身份与当前账号隔离，不能借其他人的推荐生成待办 |
| 旧重复事件、失败/不确定磁盘写入 | 同源去重；不因“模型说记下了”伪造成功；未知结果不盲目外发或重试 |
| 主 Session / 已预约延迟轮次 / 旧“值得看”功能 | 本轮不改；生活行动契机层放到 `2.7.1`，旧主人推荐逻辑重构继续后置 |

**验收限制：** Node/Python 模拟和源码集成测试不代表 DSH Windows 或真实 B站端到端已验收；需在用户设备确认账号授权、陌生人评论通知、模型结构输出、两首推荐入账、回执与公开回复一致性。

## dev.9 发行门禁审计补充（架构接线未变）

`SocialTodoReplyContract` 仍不是另一套意愿模型。它对**已生成**的肯定入账声称做保守的事实核验：先否定后肯定的复合句应分从句判断；明确声称两/三项已存，必须有足够真实持久化回执；明确称「全部」且该次已验证的原文含多个不同 BV 时，不能只保存一条就宣称全存。否则交回同一个 Life Voice 模型最多修订一次，仍不可信则不外发。此修复只改变发送前一致性校验，不改变来源校验、账本、授权或跨渠道接线。剩余自然语言语义并非穷尽保障，实机测试仍是正式发布门禁。
