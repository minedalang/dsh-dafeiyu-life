# 2.6.1 完整业务 + 专项人生记忆备份端到端 UTF-8 与老用户恢复兼容审计

## 故障根因

生产入口 `index.js` 的 HTTP `readBody` 曾以 `data += c` 接收网络数据，其中 c 为 Node.js Buffer。`String(Buffer)` 对每个 TCP 块独立执行 UTF-8 解码；若汉字或 4 字节 emoji 被切在两个块之间，解码会产生替换字符 U+FFFD，虽然 JSON 仍能解析，但与导出文件内 `manifest.files["seen.md"]` 的 SHA-256 不符。该错误发生在**浏览器把本机文件上传给恢复接口**时，和导出文件在磁盘上的正确性是两回事。完整业务备份的 `seen.md` 与专项人生记忆备份的 `life-memory/candidates.json` 均可能触发同一个字节分块缺陷；这不代表原始备份必然损坏。

### 修复链路

1. `lib/http-json-body.mjs` 以 Buffer 收集原始请求字节，达到限定大小即拒绝；在 `end` 时使用严格 UTF-8 解码器一次解码。`index.js` 通用接口保留原有 `{}` 异常兼容；**完整业务备份和独立人生记忆备份**的 `inspect`、`restore` 统一调用 `readBackupBody` 严格解析，拒绝空请求、截断 JSON、非法 UTF-8 和超限输入。
2. `lib/backup-directory.mjs` 在用户选择目录内以唯一临时文件写备份，回读比对内容并解析 JSON 后再发布正式文件名。只发布完整文件，不覆盖历史备份，也不将 Cookie、密钥写入通用包。
3. `createBackup` 和 `validateBackup` 继续在导出前检查 schema、路径、业务合法性、每个文件及 SQLite/配置 SHA-256。导入后验证每个散列；真正损坏的文件绝不能关闭校验强行恢复。
4. 恢复继续经过 `validateRestoreIdentity`、文件两阶段提交、对已衰减记忆的合并限制；外部发送回执和跨账号授权不能由历史文件自动复活。

## 测试矩阵

- 旧 `schema:2` / `version:2.4.69` 风格（无 `character-identity.json`）的 `seen.md`、`duty.md`、`out/*.md` 和设置仍可校验、恢复；旧 `dafeiyu-life-memory-backup` `schema:2` 无角色 ID 样本亦可恢复。**不声称支持未经调查的其他旧 schema。**
- Windows 风格 CRLF、重复中文、emoji（四字节）、不同 TCP 块切点以及几百个连续块；确认 HTTP 解析后文件内容不变，SHA-256 通过，恢复后逐字节相同。
- 修改导出后的 `seen.md` 文本而不更新清单必须拒绝，且原目标文件不变。
- 专项记忆导出 → 本地完整写盘 → HTTP 1～97 字节碎块上传 → SHA-256 校验 → 恢复 `life-memory/candidates.json` 与归档，覆盖动态评论候选、中文及 emoji；完整备份与专项备份都再经过真实本地 HTTP 请求验证。
- 非法 UTF-8、空请求、截断 JSON 和超过大小上限的 HTTP 请求必须拒绝；非备份接口保持原先的兼容行为。
- 伪造 `life-memory/../bili_credential.json`、未更新哈希而修改候选原文必须被拒绝，且不得写入活动记忆；私密候选不进入普通便携业务备份，却允许在经过明确确认的独立人生记忆备份中保留。
- 当目标经历已经处于 `trace` 时，导入旧备份里的 `clear` 副本不得让该经历复活为清晰记忆。
- 以上为离线可复现的实现逻辑回归。无法保证所有过往版本的特殊/被手工修改的备份均能兼容；真实文件原件不可覆盖或删除，失败应保留并诊断。

## 给已有用户的处理原则

- **不要删除、重写旧备份，也不要清空 `seen.md` 或记忆目录**。遇到 `seen.md` 校验失败，先升级恢复接口、重启 DSH，用同一份原始备份重新验证。旧接口在上传过程中损坏的数据只存在于那次请求体中，不会修改磁盘上的原始备份。
- 新接口若仍报 SHA-256 不符，代表该文件内容与清单不一致或其他未识别故障；停止恢复而不是修改清单绕过验证。可用本地离线诊断查看具体失败项，不共享包含私密记忆的原件。
- 当恢复目标存在角色绑定或已经淡化的记忆时，维持现有身份核验和遗忘不可逆的原则。

## 恢复入口与边界

| 入口 | HTTP 上限 | 原始字节解析 | 来源完整性 | 数据保护 |
| --- | --- | --- | --- | --- |
| `POST /api/bili-duty/data-backup/inspect` / `restore` | 90,000,000 字节 | `readBackupBody` 严格 UTF-8 | `validateBackup` 文件/配置/SQLite 清单 | 角色身份核对、预恢复全量快照、分阶段回滚 |
| `POST /api/bili-duty/main-session/memory/backup/inspect` / `restore` | 65,000,000 字节 | 同一 `readBackupBody` | `inspectLifeMemoryBackup` + 文件结构 | 预恢复人生记忆快照、原文件事务写入、遗忘阶段保护 |

HTML 前端原本通过 `file.text()` 一次读取所选文件，再使用同源 JSON `fetch` 上传。文件选择本身并不修改磁盘备份；网络块边界不是 UTF-8 字符边界，必须在后端统一完整解码。专项记忆备份可能包含受限隐私数据，禁止上传给第三方诊断服务。

## 未覆盖边界

- 仅保证源码明确支持的备份 `schema` 与实际测试样本；此前被损坏的软件写入、人工改动或不兼容格式，不允许重算清单绕过 SHA-256。
- Windows DSH Desktop 和用户真实 B站凭证未在本地模拟环境中连接；上线前仍建议保留唯一原始备份文件以及整个 `bili-duty` 目录的离线副本。
