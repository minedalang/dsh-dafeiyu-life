## 一张全系统图

[可编辑系统关系图](./diagrams/2.7.1-dev29-life-subsystems-overview.mmd)

Life Agent 是单一生活决策协调主体；Life Voice 提供统一的性格、情绪、成长表达，不是第二个可以授权平台写入的 Agent。视频探索、评论/私信、关系兴趣、记忆/反思、待办/契机都是专业系统与可信事实来源，而非彼此取代的「第二人格」。

- **Life 行动循环**：可信事件/契机 → 自主选择 → 读取视频/作者作品或提出一项视频写入 → 原能力网关核验账号/权限/防重/额度 → 平台实际回执 → Life 继续或结束。单轮一次写入后停止；跨评论串外发暂未开放。
- **统一回忆**：Agent 自主提出 `RecallRequest` → 当前账号/UID/隐私/遗忘硬过滤 → 明确日期按实际发生时间硬约束 → 词法与可选本地 Embedding → 带来源证据；不把向量相似当权限或真实发生证明。
- **社交分享**：已入选公开视频和当前收件人授权 → Social Intent 准备草稿 → Life 自主决定 → 现有 DM 写入网关 → 回执。不存在因相似标题擅自找其他视频的第二推荐器。
- **关系和成长**：实际互动、真实阅读和可衰减经历反馈到 Life Memory/关系/兴趣 → 统一 Life Voice 和未来选择；关系增长本身不增发信权限。

## 主动视频分享续聊的事实链修复

[可编辑链路图](./diagrams/2.7.1-dev29-video-share-handoff.mmd)

旧缺口：`social-intentions.json` 保存主动私信草稿和已发回执，但普通私信 `dm-video-recommendation.mjs` 只读取**收到的用户视频推荐**；主人 Agent 的视频链接检验只信**当前轮读取**。因此“刚刚给你推荐的视频链接呢？”可能被错误转成搜索其他主题或否认证据。

**现实现**：

1. 主动候选源为当前真实入选 BV；只有 Life 同意且好友、账号、事实与社交授权仍有效时发送。发送文案自动附上**该 BV 的规范化 B站 URL**（标准化链接是事实元信息，不是模型捏造内容）；若草稿包含不同 BV 的视频 URL 则拒绝。
2. `social-intentions.json` 的同一成功记录保存 `accountTag`、实际接收 UID、BV、标题、`sentAt`；请求平台前预约，回执未知冻结，不建立「已发送」证据。
3. 新 `confirmed-video-share.mjs` 只读该原主账本。下一轮“给我链接”需要同 UID、当前核验账号、三天内确认为发送、仍匹配发送索引，才返回一个标准 BV URL，不能跨账号跨收件人。
4. 若同 UID 近期发了两条以上且消息没有明确 BV，返回**多条歧义候选**；不能为了流畅猜哪条。未标注账号的 dev.28 旧记录不会擅自迁移成当前身份的可引用证据。
5. 普通 DM 无论精简还是完整模式，第一轮就能获得这条可信分享摘要；错误链接或答非所问触发最多一次模型修订，仍不可信则保持沉默，不由程序代写自然回复。主人私信 Agent 使用相同事实，允许当前消息所问的已发送 BV 链接通过原链接校验和真实事实验证。
6. 完整视听、歌曲实际听过、视频由鱼鱼创作等声明仍没有由分享回执自动赋予。此变更**不新增**额外主动私信许可，也不从社交关系自动授权。

### 兼容与已知局限

- 既有 dev.28 未加账号作用域的历史主动分享记录只作为诊断历史，不把其 BV 静默升格为「当前账号刚发过」的可链接回忆；修复从 dev.29 新成功发送开始生效。
- 同一收件人的非明确信息（例如聊天话题已变但突然一句「发我链接」）可能仍需自然澄清。统一回忆不代替发送成功回执。
- 尚未实际使用用户 Windows Desktop 下载安装 639 MB 模型，也未验证真实 B站私信回执；需实机观察。
