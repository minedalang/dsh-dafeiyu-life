# 2.8.2-dev.6 · B站共享读取预算与网络退避诊断

> 开发版离线实现。仅做现有状态的管理投影；未执行 Windows full、真实 B站限流恢复或 DSH 实机验收。

## 归属与事实来源

- **读取额度事实**：原 `createBiliReadBudget` 账号运行目录内的持久账本，仍由 `acquire/guard/noteError/noteSuccess` 决定是否放行、何时冷却。新增 `activeBlocks` 仅在 `status()` 返回有限枚举，列出重叠的分钟、小时、平台冷却及登录核验，不改变门禁计算。
- **通知网络故障事实**：原 `createNetworkPollBackoff`，只由原 `check/settle/clearNetwork` 修改，未创建新读取控制器。
- **投影**：纯函数 `projectReadAvailability` 汇总两套当前状态，填入 `interactionScheduler.status().readAvailability`，在管理中心原「通知与读取节奏」展示；不新增落盘文件、定时器或平台 API 调用。
- **账号作用域**：投影仅在已有当前账号已核验的前提下提供各通道解释；账号不确定返回 `account-unavailable`，不带 UID、凭据、消息、BV、目标或模型文本；原账号切换与诊断权限不变。

## 诊断契约 `bili-read-availability/v1`

- `global`: 共享读取预算层的 `ready/deferred/unknown`；`blockers[]` 仅代码、来源层和毫秒恢复边界，不载平台原始错误；重叠原因全部保留。
- `lanes`: `dmUnread/dmList/dmMessages/socialUnread/replies/mentions`；每项 `state`、主原因、`retryAt`、`blockers[]`，明确是预算、端点保护、网络故障或平台限流后的低频恢复。
- `unavailable`：当前账号未核验、通知调度关闭或该通道未启用；`unknown`：共享预算快照不可用。二者不得显示为“可以读取”。
- `ready`：仅证明**已纳入汇总的本地门禁**在当时未阻断；绝不保证 B站实际可用、模型意愿、下一轮轮询一定运行或写入授权。
- `retryAt`：所有已知拦截中最晚到期的时间，仅代表**已知最早解除限制的边界**，不是自动重试承诺。仍有额外的调度计划/未接入平台限制时以原执行器为准。

## 生命周期与失败边界

- 诊断不修改共享计数、退避轮次或原持久化状态；多进程保护和 `-509` 安全策略未松动。
- 既有系统真实 `BiliReadDeferredError`、通知网络 lane、独立 Python 读取预约与写入平台事务互相独立；本投影不对未接入的 Python 读取推断通用可用性。
- UI 沿用原管理中心的安全只读 `/status` 入口，不提供重置 `-509` 的按钮；显式区分“共享额度未阻断”和“所有通道都可用”。
- 未实施：Life 全行为因果诊断的跨模块整合、统一 Python 全入口限流视图；这部分仍在 2.8.2 后续版本，不能用本次阅读状态代替 Life 自主选择或发送结果。

## 验收与回归

定向用例覆盖共享额度可用但网络退避、重叠平台/分钟额度保护、各端点间隔、账号未核验、未启用或停止、仅凭凭据失败分类、真实账本不消费额度及 UI 无误导。正式发布前须在 Windows 普通/管理员 PowerShell 跑全量，并于 DSH 实机核对账户切换、-509 与 DNS 恢复。
