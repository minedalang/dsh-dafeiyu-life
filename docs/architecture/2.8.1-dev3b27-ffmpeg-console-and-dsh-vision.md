# 2.8.1-dev.3b.27 · FFmpeg 控制台窗口与 DSH 图片验收定向修复

## 事实来源与范围

- 2026-11-16 14:21 的 Windows 窗口采样已经关联到 `DeepSeek Harness.exe → python.exe → python.exe → ffmpeg.exe → conhost.exe` 的短暂可见 `PseudoConsoleWindow`。可见性回执不能证明所有黑窗同源，但值得优先处理本地离线解码器。
- 2026-11-16 14:26:29 的导出仅记录 `preflight=ready`、`mcpImage=not_received`、`providerApi=not_confirmed`、`modelAnswer=not_returned`、`headless_exit_unknown`。它不能证明 Provider 不支持图片或实际发生了模型 API 请求。
- 本轮不修改 B 站写入、Life 自主权、下载权限、视频网络来源、认证、Desktop 模型路由或 MCP stdio 主进程的创建策略。

## FFmpeg / FFprobe

- 仅对 `lib/adaptive_video.py` 本地受控视频的 FFmpeg/FFprobe，和 `vendor/bilibili-mcp/mcp_server.py` 的封面抽帧，Windows 创建标志由 `CREATE_NO_WINDOW` 改为 `DETACHED_PROCESS`（若系统不提供该常量则回退到 `CREATE_NO_WINDOW`），仍保留 `SW_HIDE` 与已有标准流重定向、超时、安全输入限制。
- 在 MCP 供应商脚本中使用专用 `_detached_windows_ffmpeg_child()`，绝不改变用于记忆模型、ASR 或独立视觉 DSH 的 `_hidden_windows_child()`。禁止将脱离控制台模式扩展给 MCP stdio，以免破坏进程间通信。
- **Windows 实机门禁**：先执行真实合成视频解码自检，再在观察视频 Debug 时运行窗口事件采集；只有同时确认解码成功且原先的 FFmpeg 可见窗口不再出现，才能关闭黑窗故障。云端 Linux 无法验证 Windows 控制台策略。

## DSH 图片验收

- Headless 视觉的单一只读 MCP 服务配置增加 `failOnStartupError: true`。如果 MCP 初次连接/工具发现失败，DSH 不应继续进行缺少图片工具的模型回合。没有增加其他 MCP 工具或授权。
- `vision_dsh.py` 的结构化诊断新增子进程退出码、stdout/stderr *是否有内容*；Node 端持久化仅存白名单 `cliProcess/cliExitCode/cliStdout/cliStderr`。绝不保存原始模型请求、返回原文、stdout/stderr、API Key、路径或请求 URL。
- 无真实 MCP 图片回执仍失败关闭，独立 MCP 预检不能代替 DSH 内图片回执，图片回执也不能代替模型最终回答及人工验收。
- **未解决的环境依赖**：截至 14:26 的 `exit=1` 根因仍未知，新版要再做一次 Windows 实机验收，带上新的安全阶段回执才能进一步区分 MCP 初始化与 Provider/附件问题。不能声称本版已成功识图。
