## 统一层归属检查

| 入口 | 统一层与唯一事实源 | 权限与故障边界 |
| --- | --- | --- |
| 私信和评论的真实回复 | `InteractionBatcher` 复用 `SocialContextAssembler`、唯一 Life Voice、既有 DM/评论账本 | `SocialPolicyGate`、平台配额、退订/隐私、`SocialSendTransaction`，仍不允许模型授予权限 |
| 归属判断 | `SocialDecisionOwnership.route` → **现有** `SocialHandoffFence` | 每个账号/渠道唯一 owner、持久 generation；异常文件停止，不退回 legacy |
| 模型决策至平台发送 | `attachSocialProof` 与 `socialSendOwner` | 模型完成后才产生不可直接外发的本地归属版本标签；切号或切主后旧草稿不能发送 |
| 特殊写入/视频推荐 | 继续使用 `legacySocialWrite`、主人指令、回访与分享原适配器 | Life 渠道不借用旧 owner 的权限；不能因普通回复接管而偷偷启用其他发送入口 |
| 维护切换 | 人工维护接口 + 已有 fence 的 `reserve/switchOwner/releaseDecisionOnly` | 要求总开关暂停、账户核验、明确确认、旧操作清零、发送事务无未知结果；只允许评论渠道试点 |

## 已实现的生产路径

1. 旧版数据无归属文件时仍是 `legacy`。`active/shadow/off` 模式**不能自己完成切换**。维护接口仅支持 `comment`，不对正常 UI 提供开关。
2. 操作员先关闭 B站生活总开关，并关闭旧可信评论 Agent 与待办自动回访。维护接口从**已核验账号**读取不透明账号标签，锁住评论渠道、排空已有旧决策和发送，检查同渠道 `attempted / uncertain / incomplete` 必须全部为 0。只有这时才原子写入该账号/渠道的 `owner + generation`。
3. 锁住的渠道对两种所有者都拒绝生产行为。持久写入后才释放锁；若进程中断，保留未完成锁，不自动释放。旧 owner 的模型决策、原平台发送入口会被拒绝；正常评论回调以 `life-agent` 归属调用原统一 `InteractionBatcher`，使用原情绪、人格、记忆、兴趣与关系上下文，并继续遵守既有权限与回执。
4. 返回的模型选择会在本地附加 `owner/generation/accountScope` 校验材料；评论、@ 的续聊消息以及私信普通/延迟消息传递该材料。真正发送前重新核对。如果切换、切号或生命模式暂停，拒绝该旧稿。这个本地材料**不是平台发送许可证**，模型文本不能覆盖它。
5. 经过同样暂停、清空在途、事务检查和人工确认后可切回 `legacy`；不清空旧发送账本，也不会重发原始事件。其他账号和渠道不受影响。

## 刻意尚未完成

- **私信切换入口尚未开放**：主人专属私信 Agent、旧回访、好友视频推荐等仍有独立决策来源。普通 DM 决策与发送接口已支持归属版本，但不能据此宣称 DM 已正式接管。
- **评论仍是可控试点，不是正式发布**：真实 B站 回执、Windows 进程并发与登录身份、同一账号不同渠道的线上交接、异常回滚尚未验收。未经实机与维护者确认，不应在实际账号执行切换。
- **Life 社交生产决策复用原统一社交模型/上下文与权限层**，并没有另建一个模型或记忆；Life 的匿名快唤醒保持只读，不等于独立发送决策。视频兴趣推荐主动私信暂不切入 Life owner。
- 仍缺真实经历→人格/兴趣→跨日行为因果，以及 72 小时稳定运行证据；`lifeTransitionReadiness.releaseReady` 仍为 `false`。
