# 2.8.2-dev.22 · 首轮档位预算与可核验的语义候选

> 开发候选，相对 `2.8.2-dev.21`；尚无真实 Windows/DSH/CDN 实机验证，不能发布为稳定正式版。

## 统一层归属与安全边界

- **行为主体**：Life 先自主选不看/仅了解文字/看第一轮低清画面；选择“看看画面”不等于判断视频值得真实原视频精查。
- **唯一事实**：官方 videoshot 图像索引及取帧回执给出真实采样时间；视觉模型文字、PBP 曲线与像素变化只为候选线索，不是可信事件或可执行指令。
- **账号/授权**：沿用当前 `trustedLifeAccountTag()`、视频视觉互斥锁、已有 Life willingness 凭据与共享读取预算；无公开写操作，无任意 URL 或时刻注入。
- **生命周期**：第一轮读取完取得校验后的 `preview_frames` 和 `preview_visual_analysis`，才生成候选；Life 第二次愿意选局部后才开始 MP4/DASH/FFmpeg。skip、defer、阻断都不额外取帧。
- **失败恢复**：取不到可信低清画面，不能返回虚假的“全片看过”；PBP/视觉模型推荐缺失则保守回退到时间差异候选；模型产生未采样时刻直接丢弃。

## 实现

1. `executeWatchVideo` 不修改 Life 主观 `viewDepth`。当且仅当真实 Life 已选择全局看图，或主人明确触发完整两阶段调试时，底层 Python 的本次**全局采样**使用配置档位的完整 `deep` 取帧额度。此处的 `deep` 仅是内部旧采样 API 的预算选择，不是 Life 已决定局部精查；其它单阶段与 skim 路径不扩权。
2. Python 分镜仍遵循最多 48 源拼图、1400 缩略格、40M 解码像素、8MiB 图片数据与 12/24/48 张最终代表帧。实际取帧不足时允许少于上限；每 12 张组成一张分镜。
3. 已有 DSH/本地视觉模型观察全局图时，可明确建议最多四个 `复查候选：[MM:SS] ...`。`video-focus-review.mjs` 只接受本次已核验 `frameTimesMs` 内的时刻；候选不满足真实性时不进入 Life 菜单。
4. Python 对已选每帧提供邻格变化评分；可只读获取官方 PBP 热度曲线，为**已选中**的时间点提供观众活跃度信号。没有 PBP 就忽略，不取 XML；PBP 不参与第一轮代表帧选取，不代表内容重要性。
5. 视觉语义建议优先，热度与像素差异及时间覆盖提供补位；最多四个候选时间窗可以集中在某些时段，不按四等份强行指定。Node 证据验证器接受新版低清分镜 `sampler_version=7` 并严格校验所有附加分数的范围、时间来源；旧 v5/v6 回执保留兼容。
6. 局部原视频复查继续使用第二次 Life 意愿核验、同 BV/当前账号、网络总预算、真实媒体来源和 FFmpeg 证据校验；不自动把语义推荐转成下载。

## 验收

- 本地测试覆盖真实处理函数接线：Life 未在看片前选 deep 也可按档位做全局采样；普通单阶段观察不被暗中加档；48 张图可组成 4 张分镜；v7 证据链承认合规时间与拒绝伪造热度；模型建议只能指向已取样时间；拒绝/延期不会执行局部下载。
- Windows/DSH 必测：设置页保存 48，完整两阶段验收第一次 `visual.sampling.frame_budget=48`、`frameTimesMs` 长度不超过 48、分镜图最多 4 张；视觉模型实际收到对应 JPEG。即使 Life 看后拒绝深入，也应保持这一第一轮真实回执。PBP 不可用时须看到 `unavailable` 而非编造高能。
- 尚未验证：真实 B站PBP可达性、第三方独立视觉模型是否准确产出合规推荐、多图模型延迟、Windows 正式全量、FFmpeg 真正可读性与登录状态。此阶段不得 `npm publish`。
