# 2.8.1-dev.3b.5 · 新用户主依赖安装与首次设置门禁

## 使用者遇到的问题

2.8.0 的 DSH 原生设置页原先仅能启动后台安装，不能保证用户知道安装完成与否。2.8.1-dev.3b.4 虽已把安装入口移至快速设置，但主依赖检查与可选 FFmpeg/Whisper 状态使用同一组请求；后者失败可能阻断主依赖按钮、日志与扫码状态的刷新。部分旧配置仍会令二维码调用错误的 Python。

## 本轮行为

1. **优先检测主依赖**：快速设置页面先独立读取 `/status`，判定当前专用 `.venv` 中是否存在 Python 与 `bilibili_api`、`mcp`、`qrcode`。缺失时显示安装入口、缺少的模块和日志；后台安装只表示已启动。
2. **明确等待与失败**：`installPhase` 分别表示 `not-ready`、`installing`、`failed`、`ready`；正在安装时刷新日志与当前状态。失败保留原安装日志并允许人工重试，既有就绪环境不强制重装。
3. **保护扫码环节**：依赖未就绪时，前后端均不允许开始扫码。二维码绘制固定使用专用 `.venv` 的 Python，避免旧的 `pythonPath` 设置指向没有安装 `qrcode` 的解释器；绘制失败时返回明确修复提示，不能返回 `ok:true` 和空图片。
4. **可选能力不挡路**：FFmpeg 和 Whisper 的状态接口读取失败时，在可选能力行显示错误，不会撤销已经核实的主依赖状态或锁住 B站登录。
5. **安全**：执行主依赖安装必须来自本机同源管理页。二维码登录 URL / key 不会写入诊断日志，旧用户的 Cookie、UID、Life 账本、模型设置不因安装失败而被更改。

## 验收范围与后续

离线测试覆盖无依赖新用户、扫码门禁、主依赖与可选组件检测隔离、本机同源限制、伪就绪但二维码损坏的失败处理；不是 Windows、macOS、Linux 的全新机器安装成功证明。后续须在全新 DSH Home 实机执行：点击安装、等待完成、检查包导入与日志、扫码、在线核验、重启账号绑定和 Headless 模型验证。所有对外平台写权限保持原门禁。

本轮为 **2.8.1-dev.3b.4 → 2.8.1-dev.3b.5** 独立 Patch，不涉及正式版 2.8.0 Hotfix 或完整视频语义理解；音画语义核对将在后续批次继续推进。
