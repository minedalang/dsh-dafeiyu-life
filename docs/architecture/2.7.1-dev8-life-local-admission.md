# 2.7.1-dev.8 · Life 同进程机会排他与 RC10 测试收口（未发布）

> 当前生产源码的**局部安全优化**，不是持久全局 Life 候选池。本轮不扩大任何 B站外发授权、不增加独立决策模块、保持 `releaseReady=false`。

## 统一层归属检查

`经原场景核验的候选 → LifeWillingness.decide → 进程内账号机会准入 → 原 Life 模型 → 原凭证与平台安全事务 → 原真实执行回执 → 原记忆/兴趣/关系/人格反馈`。

- 唯一意愿契约：`lib/life-willingness.mjs`；唯一模型预算：`autonomous-planner.json` 与原跨进程锁；真实行为事实仍取自原渠道回执、不是本层的意愿许可。
- 业务入口继续由原 DM、评论、回访、动态、视频探索与 Python MCP 提出候选；不直接触碰发送者、UID 授权、聊天正文、长期记忆或平台数据库。
- 每账号、每宿主进程同时允许一个正在模型选择或已有未结算批准的机会。之后抵达的候选返回 `action=defer,reason=life-choice-in-progress`，不伪装成鱼鱼自愿 `skip`。
- 一个 140ms 机会窗口最多 8 个候选；超过容量的项目返回 `defer,reason=life-opportunity-window-full`，不再创建第二个模型选择与第二份批准。
- 成功、失败或未知的 Life 回执会释放本进程候选准入；真实 B站不确定发送仍由**原跨进程发送事务冻结**。凭证过期亦释放本进程准入；结果超时不得作为自动重发授权。
- 原账号作用域、意愿证明 10 分钟上限、视频动作桥 90 秒票据、安全暂停与真实回执不变。

## 不能误读的限制

1. 该准入只约束**同一 Node.js 进程**；两个 DSH 进程之间还没有共享行动排他租约、持久化候选队列或崩溃恢复，不能作为正式 RC 的全局唯一性证明。
2. 由原渠道负责维护 `defer` 的重试语义。例如无 P6 续行的社交消息仍留待重试，视频/动态时钟可能跳过本次机会。**超过 8 的候选不保证公平轮转或跨进程持续存在。** 下一步必须实现容量、到期、重试和消费者确认都可审计的持久候选池。
3. 多场景候选合并仍以 `scene=main,uid=''` 获取通用世界上下文。关系/接收者画像未作为逐候选匿名摘要参与这次比较，需要后续在不泄漏其他 UID 或私信原文的前提下补齐。
4. `life-decision-traces` 仍为匿名诊断，不能作为平台发布成功或成长因果证据；长时间运行、旧用户恢复、Windows + 真实 B站 验收仍缺失。

## 风险矩阵与验收

| 情境 | 本次处理 | 尚需解决 |
| --- | --- | --- |
| 同时 9 个候选 | 只消费一轮模型，最多一个批准；溢出延期 | 全局公平排队与续行 |
| 上轮模型尚未结束，新窗口又抵达 | 拒绝第二次并行批准，返回技术性延期 | 跨进程相同作用域锁与故障恢复 |
| 原批准未收到真实执行回执 | 本进程临时阻断另一个自主行动，直到回执或过期 | 统一持久调度记录与人工核查未知结果 |
| 账号切换/暂停/模型错误 | 不产生可跨账号复用的批准 | 双账号实机与发送冻结验收 |
| 成功评论后自然动态 | 修正 RC10 的脆弱静态测试定位，生产原调用链不改 | 真实 B站 回执与模型自然度 |
